## What it is
The way to put [[status-quo]] (a panel of small information widgets on the desktop) on a computer in one step, and to check that a computer can run it. A person pastes one line into a terminal, or downloads one file, and the panel opens. Nothing has to be installed first: no compiler, no extra library, no fix by hand. The parts live in the public repository `yujideluca/status-quo`: two one-paste scripts (`tools/get.sh` for Linux, `tools/get.ps1` for Windows), a ready-made Linux package, a one-file Windows installer (`status-quo-setup.exe`), the program's own commands `install`, `uninstall`, `launch`, `stop` and `doctor` (a compatibility check), and the tests that run all of this on machines with nothing preinstalled. The requirements, numbered statements of what the project must do, are SQ-41 to SQ-43 and SQ-45 to SQ-48 in `docs/REQUIREMENTS.md`. The current version is 0.1.4 (2026-11-18).

## What it does
**Linux.** The README line is `{ curl -fsSL https://raw.githubusercontent.com/yujideluca/status-quo/main/tools/get.sh 2>/dev/null || wget -qO- https://raw.githubusercontent.com/yujideluca/status-quo/main/tools/get.sh; } | sh`. It needs one of the two download tools `curl` or `wget` and any standard shell (`sh`). `get.sh` downloads the package for the processor (`status-quo-linux-x86_64.tar.gz` for ordinary PCs, `status-quo-linux-aarch64.tar.gz` for 64-bit ARM processors), compares its SHA-256 (Secure Hash Algorithm 256) checksum, a fingerprint of the file, with the `.sha256` file published beside it (when they differ it stops and installs nothing), unpacks it and runs the `install.sh` inside (the file `tools/install-prebuilt.sh`). That installer asks the program which drawing libraries (shared system files that programs use to open windows and draw) are missing (`status-quo doctor --libs`) and installs the packages that hold them with the system's package manager, the tool a Linux system uses to install software (`apt`, `dnf` or `yum`, `pacman`, `zypper` or `xbps`), asking for the administrator password once and only when something is missing. A library that cannot be installed does not stop the installation. It then runs `status-quo install` for the current user, starts the panel with `launch --verify`, which waits and reports failure when the panel did not stay open, and prints the `doctor` report. In a terminal with no desktop session it installs and says the panel opens at the next login.

**Windows 10 and 11.** The README line is `irm https://raw.githubusercontent.com/yujideluca/status-quo/main/tools/get.ps1 | iex`, for the PowerShell that every Windows has (version 5.1) and for PowerShell 7. `get.ps1` downloads `status-quo-setup.exe` and its checksum, compares them and runs the installer. The script never calls `exit`, so a failure leaves the window open with the reason. `status-quo-setup.exe` can also be downloaded from the release page and double-clicked; it carries the program inside. It installs to `%LOCALAPPDATA%\status-quo\bin\status-quo.exe` without administrator rights, adds a start entry for sign-in (`status-quo.vbs` in the Startup folder), starts the panel and prints the `doctor` report. The README shows this download first, as the way that needs no typing, and the PowerShell line second.

**Where the panel appears (SQ-48, since version 0.1.4).** After any of these installs the panel sits on the desktop background: it has no title bar, stays behind the other windows and, on Windows, has no button on the taskbar (the bar at the bottom of the screen) and ends above it. An ordinary window with a title bar is a setting that is off by default: the checkbox *Floating window* under *Desktop behavior* in the panel's Customize tab, or the command `status-quo floating on` (and `off`). The panel restarts itself to apply the change. In the repository since 2026-11-19 (after 0.1.4, not yet in a release) the Windows panel is also absent from the Alt+Tab window switcher and stays visible when *Show desktop* (the Windows key with D) clears the screen; the Windows install test checks both (`tools/install-test/windows.ps1`, step PartOfDesktop) and closes a real console window to prove that the panel does not depend on the terminal that started it (requirement SQ-49). That test passed with the locally built installer on Windows 10 and Windows 11 virtual machines on 2026-11-19. The step looks at 25 points spread over the panel, because a test machine can have a window of another program open over part of it that *Show desktop* does not put away (on GitHub's Windows Server 2025 machine a "System Properties" dialog box lies there): such a window is named in the output and accepted, while the panel seen at no point, or the desktop itself over it, fails the test. If *Show desktop* is still on from an earlier run that stopped half way, the step switches it off first. Before 0.1.4 the panel opened as an ordinary floating window on Windows and on the GNOME desktop; the code behind the placement is described on [[status-quo]].

**The program's commands.** `status-quo install` copies the program, writes the start-at-login files and the hooks (small commands that the assistants Claude Code and Codex run on their own events), and records every file it wrote, with a fingerprint, in a manifest, a list file (`install.json`). It never overwrites a managed file it did not install; `install --adopt` is the deliberate way past that and keeps the old file as `<file>.before-status-quo`. When a file is in the way, the installation stops, changes nothing and says so, and the message tells how to repeat it with `--adopt` using the installer of that system (requirement SQ-51, since 2026-11-19, not yet in a release): on Windows `status-quo-setup.exe --adopt`, or `$env:SQ_SETUP_ARGS = '--adopt'` before the one-line command; on Linux `sh install.sh --adopt`, `bash tools/install.sh --adopt`, or `| sh -s -- --adopt` at the end of the one-line command. Before that change the Windows message named only `status-quo install --adopt`, a command of the program that was not installed, and the Windows installer had no such option. The Windows install test runs the case for real: it puts a file where the program goes, expects the refusal with that advice and the file unchanged, then installs with `--adopt` and checks the kept copy; this passed on a Windows 11 virtual machine and on GitHub's Windows machine in both PowerShell versions on 2026-11-19. The Linux wording is checked by a unit test only. `status-quo uninstall` removes what the manifest lists and keeps settings and history. `status-quo stop` ends a running panel. `status-quo floating on` or `off` switches the Floating window setting described above. `status-quo doctor` prints in plain language what is fine, what is a warning and what blocks the program, and exits with an error status only for a blocking problem.

**Fallback.** On a processor other than x86-64 and ARM64, or on a system built on the C library musl instead of glibc (for example Alpine Linux), `get.sh` downloads `tools/install.sh`, which builds the program from source and installs Rust (the programming language's compiler) by itself. This path is not covered by the bare-machine tests.

## How it does it
**Nothing to preinstall.** The downloads ask the system only for what a clean system has. The Linux program is built inside the `manylinux2014` container image, an old Linux kept for building programs that must run everywhere, so it needs glibc (the GNU C library, part of every mainstream Linux) 2.17 or newer; its drawing libraries are loaded when it starts, not at link time. The Windows programs are built with the C runtime inside them (`crt-static` in `.cargo/config.toml`), so they do not need the Visual C++ runtime, a separate Microsoft library package that a new Windows lacks. `tools/check_binary.rs` reads each built file and fails the build when it asks for a library outside a short list or for a newer glibc. On Windows the panel draws with OpenGL and falls back to DirectX 12 (two drawing interfaces of graphics hardware), which also works on a PC with no graphics driver.

**Start at login.** On Linux with the service manager systemd the program runs as two user services (`status-quo-collector.service`, `status-quo-panel.service`) and a desktop autostart file (`~/.config/autostart/status-quo.desktop`) starts them at login; without systemd the program starts and stops itself as plain processes. On Windows, `uninstall` runs from the installed program, and Windows does not delete the file of a running program: the file is moved aside and a hidden command deletes it a moment later. The README uninstall line ends with `| Out-Host` because the program has no console window and PowerShell would otherwise not wait for it.

**Proof by real runs (SQ-47, ADR-0006).** An ADR (architecture decision record) is a short document for one structural decision. `docs/adr/0006-installers-proven-on-bare-machines.md` records the rule that only a real run proves an installer. The workflow `.github/workflows/packages.yml` runs on every push (called by `quality-gate.yml`) and before every release (called by `release.yml`); a workflow is a set of jobs that the continuous integration (CI) service of GitHub runs automatically. Its jobs:

- `linux-package` builds the two Linux packages with `tools/package-linux.sh`.
- `linux-install` starts a bare container (an isolated minimal system) of each of 15 systems: Ubuntu 18.04, 20.04, 22.04 and 24.04, Debian 12 and 13, Fedora, Rocky Linux 8 and 9, AlmaLinux 10, Arch Linux, openSUSE Leap 15.6 and Tumbleweed, Void Linux, and Debian 12 on ARM64. In each, `tools/install-test/linux-bare.sh` first asserts that no drawing library is present, then runs the README line as written (`tools/install-test/readme-command.sh` copies it from the README), first without a screen, then with a virtual screen, then again over the running panel as an update. It asserts that the panel process runs, saves a screenshot of the panel, and runs `doctor`, `stop` and `uninstall`.
- `linux-user` does the same as an ordinary user with systemd on the GitHub machine, after removing two of the libraries.
- `linux-gnome` (since 0.1.4) starts Mutter, the window manager of the GNOME desktop, as a Wayland session (Wayland is the newer of the two Linux display systems) on a virtual monitor, installs the package and reads from the window manager what the panel's window is (`tools/install-test/linux-gnome.sh`): below the other windows and off the taskbar by default, an ordinary framed window with the Floating window setting on, and back again, with the same process through both switches.
- `windows-package` builds the installer, checks both programs with `check_binary`, and runs the README line with `tools/install-test/windows.ps1` in Windows PowerShell 5.1 and in PowerShell 7: the shell must stay open, the checksum must be verified, the panel must run, and the README uninstall line must remove the program, the sign-in entry and the folder. Since 0.1.4 it also checks the placement: the installed panel has no title bar, lies inside the free screen area at its right edge, stays behind another window also after being clicked, gets a title bar with the Floating window setting on and loses it again.
- `linux-layer-shell` (since 0.1.6) starts sway, a Wayland desktop that offers layer-shell like KDE Plasma and Hyprland, on a virtual monitor, installs the package with its own `install.sh` and checks that the panel chose layer-shell, did not stop with an error, keeps running, and that a screenshot taken with `grim` shows the panel over more than 5% of the monitor (`tools/install-test/linux-layer-shell.sh`). Version 0.1.5 stopped at start on such desktops, and no job saw it.
- `install-proof` succeeds only when all of the above succeeded. Branch protection, the GitHub setting that refuses changes to the main line of the code (`main`) unless named checks passed, requires three: `gate` (the project's own quality checks, see [[checks-status-quo]]), `windows` (build and tests on Windows) and `packages / install-proof`.

A test in `crates/desktop/tests/docs.rs` (`installation_is_proven_by_real_runs_never_by_dry_runs`) fails when a workflow uses `--dry-run` or `--check-only` as an install test, or when the release can be published without the `packages` job. `crates/desktop/tests/installer.rs` still runs the scripts against fake systems; those tests check the scripts' logic only and are not counted as proof of installation.

**Release.** A release is a published version with its download files on GitHub; a tag is a name given to one exact state of the code. Pushing a tag that starts with `v` runs `release.yml`: `packages` (all the installs above), then `publish` (attaches the two Linux packages, the Windows installer and their checksums to the GitHub release), then `published-linux` and `published-windows`, which run the README lines against the published files on five bare Linux systems and in both Windows shells. Since 0.1.6 three more steps follow. `announce` uploads `version.txt`, the file installed trays read to learn the newest version, only after those two jobs passed. `previous` finds the release before this one. `published-update-linux` (in a bare Ubuntu container, and as an ordinary user with the panel as a systemd user service) and `published-update-windows` install that previous release with the README line, with its first update check shortened to 20 seconds, and wait up to ten minutes until its running panel has installed the new release by itself (`tools/install-test/linux-update.sh`, `windows-update.ps1`). Releases before 0.1.6 have no self-update, so the first release these steps can test is 0.1.7. `release.yml` can also be started by name for a tag, which the weekly update workflow of [[status-quo]] does, because a tag pushed with a workflow's own key starts no workflow.

**Updates (SQ-54, `docs/adr/0007-updates-through-github.md`).** An installed tray keeps itself current: the panel reads `version.txt` of the newest release three minutes after it starts and then every six hours, downloads the file for its system when the version is higher, refuses it unless its checksum matches, and runs that release's installer (details on [[status-quo]]). The downloaded Windows installer carries no "from the internet" mark, so SmartScreen does not ask; a new version that needs a system library the old one did not need is installed without it, and `status-quo doctor` names what is missing.

**State on 2026-11-19, evening.** The self-update, the layer-shell fix and the job `linux-layer-shell` are on `main` (commit 7631206). CI run 44615214593 passed all 24 jobs on exactly that commit; in `linux-layer-shell` the real panel chose layer-shell on sway and covered 31.3% of the virtual monitor. The first run of that job had failed because the test looked for `panel.log`, which is written only when the panel runs as a plain process; on the GitHub machine it runs as a systemd user service whose output goes to the journal (the systemd log), and the test now reads both. Version 0.1.6 is not yet published as a release, so no installed tray has updated itself from GitHub yet; the published self-update jobs can first run when 0.1.7 is released. On 2026-11-19 at 21:19 UTC version 0.1.6 was installed on Giovanni's laptop from that commit with `tools/install.sh --yes --no-deps` (it had 0.1.0, which has no self-update): the panel restarted as a systemd user service, chose layer-shell on KDE Plasma, did not restart in the following 30 seconds and was seen on the desktop with its widgets. Its update check answers "404 Not Found" until a release carries `version.txt`.

## Notes
**Why versions 0.1.0 to 0.1.2 failed on other people's computers (found 2026-11-18).** `get.ps1` compared the checksum with raw bytes, so it never matched and nothing was installed; the Windows installer needed the Visual C++ runtime, which a new Windows lacks; a failure closed the user's PowerShell window; the Linux program was built on Ubuntu 22.04 and needed glibc 2.35; the Linux line needed both `curl` and `bash`; the installer needed systemd, stopped on distributions it did not know, and printed "Done" without checking that the panel had started. The cause behind all of them: every installer test until then was a dry run (the script prints its steps without doing them) or used faked inputs, and none ran the real command on a clean machine. The first real runs found three more defects, now fixed: minimal Debian and Void systems have no `kill` program, so an update never stopped the old panel; on Windows the panel kept the installer's output pipe open, so a script that captured the output waited forever; and the DirectX fallback had been compiled without a DirectX backend.

**Limits.** In version 0.1.4 the Windows *Show desktop* shortcut (the Windows key with D) hid the panel like any window; version 0.1.5 (2026-11-19) no longer has this limit. On a Windows without usable OpenGL the panel draws through DirectX; up to 0.1.4 that could not make a window see-through, so the background was solid and Customize said that the opacity setting has no effect there. Since 2026-11-19 (SQ-52) it is see-through there too when the graphics adapter accepts alpha, seen on the Windows 10 and 11 test machines; a real graphics card was not tested. Debian 11 is not tested: it is past its end of life and its package servers answer "not found" for a fresh container. The source-build fallback (musl systems, other processors) is not tested on a bare machine. `status-quo-setup.exe` is not code-signed (Giovanni decided on 2026-11-19 not to buy a certificate), so Windows SmartScreen shows a notice ("More info", then "Run anyway") when it is downloaded with a browser; the PowerShell line does not show it.
