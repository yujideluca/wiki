## What it is
A set of Python scripts in `~/dev/wiki-bench` that measure how much work a browser does to draw the wiki's map while someone moves the mouse, and that name the lines of the map's code that cause that work. They exist so that a speed claim about the map comes with a number, a spread between repeated runs and the code it concerns, instead of an impression.

## What it does
`map_bench.py` loads one build of the wiki in a headless Chrome (Chrome without a window), plays a gesture and records a browser trace: for each animation frame the time spent in JavaScript, style, layout, paint and commit on the main thread, plus the raster work (turning shapes into pixels) on the other threads. The gestures are `pan` (drag the globe), `pan-fast` (a quick flick), `sweep` (the cursor moves over the globe with no button down), `zoom` (mouse wheel), `idle` (nothing happens), `hover` and `drag` (drags a dot, not the globe).

`compare.py` runs several builds under several gestures for several rounds. It rotates the order of the builds from round to round and measures the first build once more at the end of every round; the gap between its two runs (a drift of the machine between -17 % and +18 % was seen) tells how large a difference must be before it counts as a result. It prints the median and the minimum-maximum for frames drawn, mean and 95th-percentile frame time, main-thread busy time and raster time.

`callprof.py` finds the code. For one build and one gesture it runs the page three times: under Chrome's CPU sampler, under exact call counting, and with a `MutationObserver` (a browser feature that reports every change to the DOM, the Document Object Model, the page's tree of elements) that counts the attributes written per mouse event. `elmmap.py` turns a compiled name such as `$author$project$Motion$step` into `src/Motion.elm:89`. `callcmp.py` puts the profiles of several builds side by side, per mouse event and per frame, with the page writes, the hottest compiled lines and a ranked list of what to optimise first. `framelog.py` shows when a build asks for animation frames and which events the page received. `callers.py` shows which app functions sit above every sample that contains a given runtime function. `functional.py` checks with real mouse input that hover, click, dragging the globe, dragging a dot and zooming still behave the same in a changed build, and `shots.py` takes pictures to compare by eye.

## How it does it
It drives Chrome through the DevTools Protocol (the remote-control interface of Chrome) with the `websockets` library. Mouse input is open loop: `play()` in `map_bench.py` sends every event at its scheduled time and does not wait for the page to answer. This was added after `framelog.py` showed the same flick lasting 179 ms in one build and 826 ms in another when each event waited for the page's answer: a slower build then received a longer gesture, and the comparison favoured the wrong build. The Elm compiler keeps function names in `--optimize` builds but writes no source map, so a line below function level is reported as the compiled line under its Elm function. Builds come from `~/dev/wiki-globe-sandbox` (a worktree of the wiki repository holding variants of the map's coordinate code); `build.sh` deletes and recreates a build folder, so any `http.server` serving it must be restarted.

What the tools found so far is in `globe/RESULTS.md` (rounds 3 to 10). With open-loop input, a variant of the map (v6) that keeps the spring state in one array, finds the dot under the pointer by camera maths instead of invisible page elements, and stops updating hover while the globe is dragged, cut the mean frame time of a pan from 11.8 to 6.8 ms (-42 %) and of a cursor sweep from 10.7 to 9.2 ms (-14 %), against the same map with only a CSS layer rule added (`will-change: transform` on the map's SVG, Scalable Vector Graphics, the drawing format of the map, which alone cut raster time by about 30 %). Two ideas that looked promising gave no measurable gain and were not adopted: moving a picture with one CSS transform between exact redraws, and drawing the lines as a few paths or giving the page's elements keys. Zoom did not improve and its raster time (drawing done on other threads) rose by 60-75 %. Round 9 traced this to the removal of the invisible hit discs: the old map with only its discs hidden shows the same rise (1,363 to 2,074 ms against 2,028 ms for the new map), and the main thread did not get slower. Why the browser needs more raster time without them is not known. Round 10 measured the real phone (a Motorola edge 50 fusion, Chrome over `adb forward`; `globe/phone.py`, input by `adb shell input swipe` for swipes and Chrome's own pinch gesture, because the DevTools touch events reach the page as 3 of 50 moves and never end; a frame is Android Chrome's `ProxyMain::BeginMainFrame` with a commit, 3 repeats, build order alternated). Mean main-thread time per frame, old map against the globe: slow swipe 35.5 against 12.7 ms, quick flick 34.2 against 14.4 ms, pinch 34.6 against 15.5 ms; the page produced 136 frames in the swipe against 46 and received 140 touch moves against 50. The rise in zoom raster time did not appear on the phone: raster time in the pinch was 306 ms for the old map and 242 ms for the globe. Not checked: a second phone, a temperature log, why the old build's page has more `g.node` elements (202 against 126), and a person's look at a long interaction. Round 8 then checked the same code after it was merged into the wiki repository (commits be23e36 and 1a2f508): every behaviour check equals v6, and a pan took 5.4 ms a frame against 6.2 ms for v6 and 10.2 ms for the control, which is within the noise.

## Where it sits in the pipeline
Run by hand by [[claude-code]] or Giovanni after a change to the map; its results are the evidence behind the speed notes of [[wiki-map-view]].

## Who receives its output
Files in `~/dev/wiki-bench/globe/results` (raw json and Markdown tables) and `globe/RESULTS.md`; [[wiki-map-view]] describes the map it measures.
