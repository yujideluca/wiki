## What it is
Status Quo is a desktop widget environment written in Rust: small always-visible panels on the desktop itself, without a window frame, that show how much of Giovanni's Claude and Codex usage limits is spent, token graphs, the sessions each assistant is running, recent GitHub activity and recent workflow-memory entries. The code lives in `~/dev/status-quo` and in the private GitHub repository `yujideluca/status-quo`. Start with its `README.md`. The approved scope is on [[status-quo-design]] and the layout mockup on [[status-quo-layout]]; this page describes the code as built.

Every display is a separate widget that can be removed, replaced or moved to another program, and the tray that arranges them is reusable too. KDE, the desktop shell on the laptop, is the first host; nothing portable depends on it.

## What it does
The panel has five initial widgets, instantiated for each assistant where that applies, giving seven by default: Claude and Codex account usage, Claude and Codex token history, sessions grouped by project, recent GitHub activity and workflow-memory entries. Usage shows the percentage used for the five-hour and weekly limits with reset times; it never derives a percentage from local token counts. Token graphs switch between 24 hours, 7 days and 30 days, and between per-bucket and cumulative views. Missing values are shown as unavailable, never zero.

The customization tab changes light, dark or system mode, accent colors, background opacity, text size and widget order and size, and the space between widgets. Changes preview first and can be cancelled. Widgets can be added, removed, hidden or detached. The default stacking is behind normal windows, anchored to the top-right corner; on the laptop it was seen hidden behind a maximized browser and visible on an empty workspace.

## How it does it
The code is a Rust workspace of nine packages. `sq-core`, `sq-contract` and `sq-widgets` hold the portable logic and may not use graphics, files, processes or the network; `tools/rust_architecture.rs` checks this on every gate run, because the shared checker only understands Java and Kotlin. `sq-sources` reads outside data, `sq-store` writes it atomically, `sq-collector` runs the workers and serves a versioned, size-limited socket, `sq-tray` is the reusable egui interface (egui is a Rust library for drawing interfaces), `status-quo` is the Linux wrapper and `sq-web` is a browser demonstration with invented data.

**Collector.** `crates/collector/src/lib.rs` holds the socket server and process lock, so only one collector runs per user. `workers.rs` runs one worker per source: account status, session transcripts, GitHub and memory. Each worker keeps its last valid data with a freshness and error state, so one broken source never freezes the rest. Workers watch folders for changes and fall back to 2-second polling only when a watch fails. The collector creates its own private `events` folder before watching it; before that fix, a missing folder forced polling and tripled idle CPU use. `events.rs` writes one small file per session lifecycle event, under a lock, and keeps no prompt or tool text. A Stop event means the session is waiting, not that its task is complete.

**Widgets.** `crates/widgets/src/lib.rs` (package `sq-widgets`) registers the eight built-in widget types, `quota`, `tokens`, `sessions`, `activity`, `memory`, `system`, `ram` and `gpu`, through `registry()`. Each type turns a snapshot from the collector into a view, a list of plain nodes (text, rows, notices) that the tray draws; the package cannot read files or start programs. A row keeps at most 100 entries for GitHub activity and for memory. The `system` widget (requirement SQ-30) shows the latest CPU share and package temperature as text, each above a line graph of the last ten minutes; a value that could not be read says "Unavailable" and is never drawn as zero, and "Waiting for the first samples" shows before any sample exists. Its numbers come from one collector thread (`system()` in `crates/collector/src/workers.rs`) that, every 5 seconds, reads two small kernel files through `crates/sources/src/system.rs`: `/proc/stat` (cumulative CPU time counters; the share is the busy part of the change between two readings) and the CPU package temperature sensor under `/sys/class/hwmon` (found once; `coretemp`, `k10temp` or `zenpower`, else the `x86_pkg_temp` thermal zone). It starts no program, keeps 120 samples in memory only, does nothing and bumps no snapshot revision while no system widget exists, and one sample measured about 26 microseconds of work. The same thread also reads `/proc/meminfo` for the `ram` widget (requirement SQ-32), which shows used and total memory (total minus the kernel's "available" figure) with a graph of the percentage, and swap as text. The `gpu` widget works for every GPU of any vendor, several at once, and is sampled by a separate thread (`gpu()` in `crates/collector/src/workers.rs`; readers in `crates/sources/src/gpu.rs`). The display adapter (the one the screen is driven by) is always awake, so it is read directly each time: Intel from the actual clock speed and the share of time it was not in its idle state (RC6, the chip's deep-sleep state), AMD and other vendors from the kernel's load, video memory, temperature and power files. A second, discrete GPU (for example this laptop's NVIDIA chip) switches itself off when idle and any query, even `nvidia-smi`, wakes it and keeps it awake for about 20 seconds; polling it would stop it ever sleeping. For those the thread reads only the power state from `/sys/class/drm` (reading that never wakes it) and shows "Powered down" without numbers while it sleeps. Only when the chip is awake and the thread has not touched it for 30 seconds (so something else is using it) does it start measuring (NVIDIA through one `nvidia-smi -i` process reporting every 5 seconds, others through their kernel files); after three idle readings in a row it stops, so the chip can sleep again. Unknown values stay unavailable and are never drawn as zero. The `system`, `ram` and `gpu` graphs are "compact" charts: each shares the widget's height with the others (no scrolling, and they follow the widget when it is resized vertically), and has no time or legend row, only the range on the right edge. Percentages are drawn on a fixed 0 to 100 scale; temperature and clock use a range that follows the data but is never narrower than 20 °C or 500 MHz, so a steady value is not stretched into noise (requirement SQ-33). Every widget type, not only these, now measures the room that is left under its title and controls (the token widget's range buttons may wrap onto more lines) instead of assuming a fixed amount: charts, including the token chart, split that room and follow the widget's height, and long lists scroll inside it. For an Intel GPU the figure is labelled "Awake": without administrator rights only the share of time the chip was out of its idle state (RC6) can be read, not the work it did, and a desktop keeps it awake roughly half the time. A widget also adds a notice when its source is not fresh, or has malformed or deferred records, and "Waiting for source status" before any status exists. The sessions widget shows running, waiting and blocked sessions always, completed ones for one hour, others for 24 hours, unless its `history` option is `true`. `format_utc` prints times as `YYYY-MM-DD HH:MM UTC` without reading a clock. The tests in `crates/widgets/tests/models.rs` (requirements SQ-5, SQ-6, SQ-8, SQ-10, SQ-11) check, among others, that a missing quota is not shown as zero, that projects with the same folder name stay separate, that nested agents stay under their real parent and that dates at the extremes do not overflow.

**Accounts and platforms (requirements SQ-35 and SQ-36, 2026-11-06).** The tray is meant to be shared, so nothing in it names one person's accounts or one operating system. *Accounts:* besides the default Claude, Codex and GitHub sign-ins, the configuration (`sources.accounts` in `crates/core/src/config.rs`) can list any number of extra accounts, each a kind (`claude`, `codex` or `github`), a short name, and where that tool keeps its own login: the Claude or Codex home folder, or a `gh` configuration folder (the one `GH_CONFIG_DIR` names) with its list of repositories. Nothing secret is stored: Status Quo only reads what the tool itself saved, as before. An account is named `kind:name` (for example `claude:work`); that key is what a widget's provider, a token record, a session, a usage reading and a health entry carry, so two accounts never mix. One worker (`accounts()` in `crates/collector/src/workers.rs`) reads the usage of every Claude and Codex account in turn with its own retry delay (an extra Codex account runs `codex` with `CODEX_HOME` set), the GitHub worker reads each login with its own `GH_CONFIG_DIR`, and transcript discovery walks every account folder. The Add widget menu and a widget's settings list every account, and Customize has a "More accounts" section. A widget set to an account that does not exist shows "unknown", never another account's numbers. Hook events (the live session states) still describe the default accounts only, and resuming a session of an extra account opens the tool without that account's home folder: both are known limits. *Platforms:* the code that touches the operating system is kept apart. On Linux the tray still uses the layer-shell, X11 or window hosts; on Windows 10 and 11 it is an ordinary window (the Window layer setting keeps it behind or above other windows). The link between collector and panel is a private socket file on Unix and, on Windows, a loopback network port whose number and a random token sit in a file in the user's private folder: a client must send the token first, so another user of the machine cannot talk to the collector (`crates/collector/src/transport.rs`). State lives in `%LOCALAPPDATA%\status-quo` on Windows, the program is installed under the same folder and started at login by a hidden script in the Startup folder (`windows_files()` in `crates/desktop/src/install.rs`), and private-file permissions are no-ops there because the profile folders are already private (`sq_store::private`). CPU time and memory come from `GetSystemTimes` and `GlobalMemoryStatusEx` (`crates/sources/src/system.rs`), NVIDIA GPUs from `nvidia-smi`; the CPU temperature has no driver-free source on Windows and shows "Unavailable", and Intel and AMD GPUs are not listed there. Tools such as `codex` that npm installs as `.cmd` files are found on `PATH` (`program()` in `crates/sources/src/lib.rs`), and links and session resumes are opened without a shell, so characters in a link cannot start another command. The Windows build is compiled and tested in real Windows 10 and Windows 11 machines kept on the laptop by [[vm-lab]], and the workflow file has a Windows job for the same. Results of 2026-11-06: the whole test suite (28 test programs) passes on Windows 10 (LTSC 2021) and Windows 11 (24H2), the collector runs and answers `inspect` there through the token-checked port, and install, reinstall and uninstall work and keep the user's own assistant hooks. **Contract.** `crates/contract` defines how a host registers widget types and how requests and snapshots are framed. Incompatible versions and oversized frames are rejected, and an unrelated sample widget proves that registration works without changing the tray (`crates/contract/tests/registry.rs`; the framing limits are also exercised by `crates/collector/tests/transport.rs`).

**Hooks.** The installer adds Status Quo entries to `~/.claude/settings.json` and `~/.codex/hooks.json` and keeps every existing hook. It was run on 2026-11-02.

**Compatibility layer.** `crates/desktop/src/host/` is the only code that knows how the tray is placed on a given Linux desktop, and it chooses at run time, so one program works across distributions (decision in `docs/adr/0004-host-compatibility-layer.md`). Layer-shell, a Wayland protocol that lets a program draw on the desktop layer, is used when the compositor offers it (KDE Plasma, Hyprland, sway); the tray then has no frame, is anchored to an edge or corner (`STATUS_QUO_ANCHOR`, default top-right) and draws only when something changed. On an X11 session it uses a frameless window with window-manager hints for below, off the taskbar and off the pager; asking for all workspaces is best effort because KDE's X11 compatibility ignores it. Everywhere else, for example GNOME on Wayland, it falls back to an ordinary window and says so. `STATUS_QUO_HOST=layer-shell|x11|window` forces a choice when it can work. In these two hosts the tray is bare: it has no background or title of its own, only the widgets and the three small buttons Add widget, Edit tray and Customize are visible (the connection status appears only while disconnected), and the rows of widgets are scaled so they fill the tray space exactly, with equal gaps. Customization and screenshots use the ordinary window because the layer host has no keyboard input yet.

**Edit tray (requirement SQ-29, redesigned 2026-11-02, decision in `docs/adr/0005-free-canvas-layout.md`).** The Edit tray button turns the tray into a free canvas editor that works with the pointer alone. Each widget can carry an explicit rectangle in pixels (`x`, `y`, `width`, `height`, in `crates/core/src/config.rs`); a width of 0 keeps the old flow of rows, so old configurations load unchanged, and the validator accepts widths of 120 to 8000 and heights of 60 to 8000. Pressing Edit tray first freezes what is on screen into rectangles, so nothing jumps (`freeze` in `crates/tray/src/layout.rs`). Then every border and corner of a widget resizes it on both axes to any size, and dragging the body moves it anywhere (`drag_rect`, which keeps a minimum size and never crosses the canvas corner). Widget content is switched off while editing so it cannot take the pointer from the handles. All changes happen on a draft copy: Done normalizes the canvas to its corner, records the corner's desktop position in the saved `tray` geometry and saves through the same validated configuration path as Customize; Cancel discards the draft. Widgets learn how much room they have: charts take about 55 percent of the widget height, and token controls and meter text wrap (`crates/tray/src/ui.rs`). Outside editing, the tray reports the size it wants (`desired_size`: the canvas from `free_rects` and `canvas_size`, plus the header), and the layer-shell host sizes its surface to match (`Surface` in `crates/desktop/src/host/layer.rs`, chosen by `LayerApp` in `crates/desktop/src/main.rs`): `Legacy` is the first-run corner layout, `Free` docks the surface at the saved desktop position, and `Editing` covers the whole output, transparent and above windows, so a widget can be dragged anywhere. Window hosts follow with an inner-size request instead. The docked surface is kept on the screen: `clamp_to_screen` in `layer.rs` slides a tray that a widget move made too wide or too low back inside the output, and `docked_origin` reports the clamped corner, so the header buttons stay reachable. Overlapping widgets are allowed; the tray draws each free widget in its own egui layer (an `Area`), stacked in configuration order, so the widget on top also receives the pointer where widgets overlap (test `a_button_on_the_top_widget_still_works_where_widgets_overlap` in `crates/tray/tests/layout.rs`). Only the first output is used (per-monitor placement is not handled). Checked so far: tests drive real pointer events through the tray, and an isolated run in a real compositor rendered a docked free layout correctly (both as recorded in ADR-0005, the architecture decision record (ADR) of this change; the run itself was not repeated here). A drag in the full-screen editor on the real desktop, driven with a virtual mouse by the desktop end-to-end test, was first run on 2026-11-04 (see the paragraph on desktop-wide placement below). The effect of the redesign on the idle CPU use is not measured. The change is committed on the branch `feature/free-canvas-edit-tray` (855ffd7, then f7f88de and 13e05e8 on 2026-11-04) and pushed to the remote; the continuous integration (CI) job `gate` passed on 13e05e8 (run 41943440329); the branch was fast-forwarded into `main` on 2026-11-04 (`origin/main` is now 13e05e8); the branch was then deleted.

**One gap and sticky borders (SQ-29, update of 2026-11-02 in ADR-0005).** `Config.gap` in `crates/core/src/config.rs` is the single space between widgets, in pixels: 0 to 64 (the validator rejects other values), default 10. The flow layout, the stacking of widgets without a rectangle and the editor all use it. In Customize the slider "Space between widgets" sets it; that slider in `crates/tray/src/ui.rs` runs only from 0 to 40, so 40 to 64 can come only from a configuration file (read from the code, not run). While editing, `layout::snap_rect` makes a dragged border stick to other widgets within 10 pixels (`SNAP` in `crates/tray/src/layout.rs`): a border settles exactly one gap from a neighbour's border, or flush with an aligned border, and a width or height near another widget's becomes exactly that size; gap and alignment win over size when both are near. The tray keeps the unsnapped rectangle that follows the pointer and draws the snapped one, so a widget that stuck lets go again when pulled further. The Edit tray button is disabled while Lock widget layout is on (its tooltip says to unlock in Customize). A widget added to a tray that already has explicit rectangles gets one at the top-left corner (x and y 0, width 420 pixels), so it is visible and can be dragged. When editing starts, a first-run layout taller than the space the tray had is compressed vertically to fit (`fit_to_space` in `ui.rs`). Alignment guides (requirement SQ-34, `guides()` and `snap_rect()` in `layout.rs`, painted by `paint_guides()` in `ui.rs`): while a widget is dragged, the tray draws a pink line where one of its borders lines up with another widget's border (flush, or one gap apart), a dashed blue line where their centre axes coincide, and an amber bar under (width) or beside (height) both widgets when they have the same size. All of these are sticky points within 10 pixels, tried in the order borders, centres, sizes; a candidate that would make the widget smaller than the minimum or push it off the canvas is not offered, so every position the widget sticks at has a line that explains it. The lines disappear when the mouse is released. A random test of 6,000 drags checks these properties. Unit tests cover the snapping (inside `layout.rs`, and in `crates/tray/tests/layout.rs` a border that sticks at the gap and lets go, a size that sticks, the lock, the compressed first freeze) and the configuration limits and new-widget rectangle (`crates/core/tests/behavior.rs`). The new sticky step of the end-to-end test has NOT been run on the desktop: the run was withheld because the screen was in use, so the 22-check result below predates it and shows nothing about snapping on the real desktop.

**Desktop-wide placement and Remove (SQ-29, update of 2026-11-04 in ADR-0005).** Two changes to Edit tray. First, widgets can now be placed anywhere on the desktop. Before, the full-screen editor measured every widget from the docked tray's top-left corner and stopped it at zero, so a widget could not be dragged left of or above that corner. Now `Tray::set_origin` in `crates/tray/src/ui.rs` shifts each draft widget once by the tray's desktop position when the host reports it (the host reports it after `begin_edit`, just before the surface covers the desktop; an earlier version shifted inside `begin_edit`, too early, and drew every widget at the left edge), so a position is a desktop position (still not below zero, and not above the header height, because the docked tray needs its header above the widgets); Done saves the position of the leftmost and topmost widget as the tray's desktop position (`normalize_canvas`). Window hosts are unchanged. Second, every widget in the editor shows a "Remove" button at its centre (`edit_handles` in `ui.rs`, added after the resize handles so it receives the pointer before the body drag). Pressing it removes the widget from the draft only: Done saves the smaller tray and Cancel brings the widget back. Because the centre now holds the button, dragging a widget by its body must start away from the centre; the tests and the end-to-end test do so. Tests in `crates/tray/tests/layout.rs`: `a_remove_button_in_the_widget_centre_removes_it_from_the_draft_and_cancel_restores_it`, `removing_a_widget_and_pressing_done_saves_the_smaller_tray` and `a_full_desktop_editor_places_widgets_left_of_and_above_the_docked_tray`; the gate passed. Checked on the real compositor on 2026-11-04 with the desktop end-to-end test (new step 8c: move the topmost widget far left of the docked tray, Remove then Cancel, Remove then Done), run with `STATUS_QUO_E2E_EMPTY_HOME=1`, which starts the private copy with an empty home folder because its cold read of every real transcript kept it busy for minutes and starved the virtual mouse (the idle CPU of such a run says nothing about the real load): 28 of 29 checks passed. The sticky-border step still fails (60.4 against 10 pixels, with overlapping widgets on screen) and is open; it had never been run on the desktop before.

## Engineering practices
How this project follows the golden path of [[project-template]].

### Principles
1. **Requirements precede changes**: tests carry a standalone `// REQ SQ-n` comment, and the traceability step ([[check-traceability]]) fails when a requirement has none.
2. **Portable packages stay free of input and output**: core, contract and widgets, checked by a project-specific detector with planted-defect self-tests.
3. **Everything is a removable widget**: no permanent provider slots in the tray.
4. **The gate decides**: `tools/quality_gate.sh` is the only definition of passing, and no limit is lowered to make it pass.
5. **Nothing private is stored**: no credentials, conversations or memory contents in fixtures, diagnostics or the browser demo.

## Notes
Build with `cargo build --release --locked -p status-quo`; the installer is `status-quo install` and `status-quo uninstall` reverses it. State lives in `~/.local/state/status-quo`; `STATUS_QUO_STATE_DIR` redirects it for tests. On the laptop, test runs on 2026-11-02 showed the layer-shell host with live data, the collector seeing real assistant sessions through the hooks, a mouse click changing a widget, and a 60-second idle measurement of 1.08% of one core and 195 MB combined (the graphics driver libraries account for most of the panel's 156 MB). `docs/TESTES-AUTOMATIZADOS.md` (in Portuguese, as its name says) is the record of the bug-finding tests; see [[checks-status-quo]]. Not yet observed: login startup, the 100 ms interaction limit, the full five-minute run, keyboard input in the layer host, GNOME or any other desktop than KDE Plasma, and a real X11 session. The cause of the remaining idle CPU use is open.

**Transcript discovery (requirement SQ-31).** The collector finds Claude and Codex transcript files by walking their folders and reading at most five levels. Only files count toward the 100,000-file safety bound; empty folders do not. A projects folder once held about 94,000 empty folders left by throwaway working directories, which made the old scan fail every time (token history stopped updating) and made the collector watch about 190,000 folders, nearly the system limit for file watches (inotify). Now only Claude project folders holding recent transcripts are watched (about 580 watches), plus the projects folder itself to notice new projects within 30 seconds.

**Desktop end-to-end test.** This test exercises the real tray on the real desktop, which the ordinary tests cannot do. `tools/ui_e2e.sh` builds the production program and runs `crates/desktop/tests/desktop_e2e.rs`, a Rust test marked ignored so that a plain `cargo test` skips it. The test pauses the live tray, starts a private copy with its own state folder and collector, and drives it with a virtual mouse created through `/dev/uinput` (the Linux interface for fake input devices). It then reads what the tray saved in its configuration and checks it. It covers: start, idle CPU and memory, Edit tray and Cancel, moving a widget, resizing by a corner and by an edge, Done and docking, the token controls, Add widget, Customize and Cancel, and a restart. Afterwards it restarts the live tray.

**Run it:** `tools/ui_e2e.sh` from the repository root, or `STATUS_QUO_E2E=1 tools/quality_gate.sh` to run it as optional gate step 6. **Needs:** a Wayland session, a writable `/dev/uinput` and the screenshot program `spectacle`; without one of them the script prints "skipped" with the reason and exits successfully, so a skip is not a pass. **Refuses unless the screen is free:** without `STATUS_QUO_E2E_SCREEN_IS_FREE=1` the script prints a refusal and exits with status 2, because the virtual mouse clicks for about three minutes on whatever window is in front, and one run once clicked into a maximized browser. Close or minimize windows over the right side of the screen and keep hands off the mouse first (`docs/MAINTENANCE.md` section 7); optional gate step 6 therefore needs both `STATUS_QUO_E2E=1` and this variable. **Output:** `build/e2e/report.json` (each check with `ok` and a detail, a `data` block, and the open findings) and screenshots `build/e2e/*.png`. The expected positions and numbers come from a manual test of 2026-11-02, saved in `crates/desktop/tests/e2e/manual-baseline.json`; `docs/MAINTENANCE.md` section 7 says to repeat the manual pass, update that file and extend the test whenever a major tray update lands.

**Browser demonstration (`docs/browser-demo.md`, `tools/build-web.rs`).** The package `sq-web` runs the same `sq-tray` interface in a browser with invented data, labelled as a demonstration. It does not connect to the collector or read credentials, transcripts, GitHub or workflow-memory, changes do not reach the desktop settings, and reloading restores the sample. It also registers an unrelated example build-status widget through the public widget contract, to show that no built-in provider slot is needed. `tools/build-web.rs` is a standalone Rust program, compiled with `rustc tools/build-web.rs -o /tmp/status-quo-build-web` and run from the repository root. It builds `sq-web` in release mode for the `wasm32-unknown-unknown` target (WebAssembly, the format browsers run) with `--locked`, runs `wasm-bindgen` (the tool that generates the JavaScript that loads the WebAssembly module; its version must match `Cargo.lock`) into `dist/web/pkg`, and copies `crates/web/site/index.html` to `dist/web`. With `--serve` it instead serves `dist/web` at `http://127.0.0.1:8765/` on localhost only, answers GET requests only and refuses paths containing `..`, `.`, `%` or a backslash. The variables `CARGO`, `CARGO_TARGET_DIR` and `WASM_BINDGEN` choose the tools; it never downloads any. The page needs a browser with WebAssembly and WebGL2 (a graphics interface) and must be opened through the server, not as a `file://` address. The document records one real-browser check of 2026-11-02 (open Customize, choose Light, Save changes) and three Rust tests of the browser host; this page's review did not repeat them (not verified now). Browser rendering does not establish desktop compositor, native socket, startup or source-adapter behavior.
