## What it is
Status Quo is a desktop widget environment written in Rust: small always-visible panels on the desktop itself, without a window frame, that show how much of Giovanni's Claude and Codex usage limits is spent, token graphs, the sessions each assistant is running, recent GitHub activity and recent workflow-memory entries. The code lives in `~/dev/status-quo` and in the public GitHub repository `yujideluca/status-quo` (MIT licence). Start with its `README.md`. The approved scope is on [[status-quo-design]] and the layout mockup on [[status-quo-layout]]; this page describes the code as built.

Every display is a separate widget that can be removed, replaced or moved to another program, and the tray that arranges them is reusable too. KDE, the desktop shell on the laptop, was the first host; nothing portable depends on it, and the program also runs on other Linux desktops and on Windows 10 and 11. The current version is 0.1.4 (2026-11-18).

## What it does
The panel has five initial widgets, instantiated for each assistant where that applies, giving seven by default: Claude and Codex account usage, Claude and Codex token history, sessions grouped by project, recent GitHub activity and workflow-memory entries. Usage shows the percentage used for the five-hour and weekly limits with reset times; it never derives a percentage from local token counts. Token graphs switch between 24 hours, 7 days and 30 days, and between per-bucket and cumulative views. Missing values are shown as unavailable, never zero.

The customization tab changes light, dark or system mode, accent colors, background opacity, text size and widget order and size, the space between widgets and, since 2026-11-06, an option to follow the wallpaper colours. Changes preview first and can be cancelled. Widgets can be added, removed, hidden or detached. The default stacking is behind normal windows, anchored to the top-right corner; on the laptop it was seen hidden behind a maximized browser and visible on an empty workspace. Since version 0.1.4 (requirement SQ-48) this desktop-background placement is the default on every supported system, and Customize has a *Desktop behavior* section with a *Floating window* checkbox, off by default, that turns the tray into an ordinary window with a title bar.

## How it does it
The code is a Rust workspace of ten packages. `sq-core`, `sq-contract` and `sq-widgets` hold the portable logic and may not use graphics, files, processes or the network; `tools/rust_architecture.rs` checks this on every gate run, because the shared checker only understands Java and Kotlin. `sq-sources` reads outside data, `sq-store` writes it atomically, `sq-collector` runs the workers and serves a versioned, size-limited socket, `sq-tray` is the reusable egui interface (egui is a Rust library for drawing interfaces), `status-quo` is the desktop wrapper for Linux and Windows, `sq-web` is a browser demonstration with invented data, and `status-quo-setup` is the one-file Windows installer ([[status-quo-install]]).

**Collector.** `crates/collector/src/lib.rs` holds the socket server and process lock, so only one collector runs per user. `workers.rs` runs one worker per source: account status, session transcripts, GitHub and memory. Each worker keeps its last valid data with a freshness and error state, so one broken source never freezes the rest. Workers watch folders for changes and fall back to 2-second polling only when a watch fails. The collector creates its own private `events` folder before watching it; before that fix, a missing folder forced polling and tripled idle CPU use. `events.rs` writes one small file per session lifecycle event, under a lock, and keeps no prompt or tool text. A Stop event means the session is waiting, not that its task is complete.

**Widgets.** `crates/widgets/src/lib.rs` (package `sq-widgets`) registers the eight built-in widget types, `quota`, `tokens`, `sessions`, `activity`, `memory`, `system`, `ram` and `gpu`, through `registry()`. Each type turns a snapshot from the collector into a view, a list of plain nodes (text, rows, notices) that the tray draws; the package cannot read files or start programs. A row keeps at most 100 entries for GitHub activity and for memory. The `system` widget (requirement SQ-30) shows the latest CPU share and package temperature as text, each above a line graph of the last ten minutes; a value that could not be read says "Unavailable" and is never drawn as zero, and "Waiting for the first samples" shows before any sample exists. Its numbers come from one collector thread (`system()` in `crates/collector/src/workers.rs`) that, every 5 seconds, reads two small kernel files through `crates/sources/src/system.rs`: `/proc/stat` (cumulative CPU time counters; the share is the busy part of the change between two readings) and the CPU package temperature sensor under `/sys/class/hwmon` (found once; `coretemp`, `k10temp` or `zenpower`, else the `x86_pkg_temp` thermal zone). It starts no program, keeps 120 samples in memory only, does nothing and bumps no snapshot revision while no system widget exists, and one sample measured about 26 microseconds of work. The same thread also reads `/proc/meminfo` for the `ram` widget (requirement SQ-32), which shows used and total memory (total minus the kernel's "available" figure) with a graph of the percentage, and swap as text. The `gpu` widget works for every GPU of any vendor, several at once, and is sampled by a separate thread (`gpu()` in `crates/collector/src/workers.rs`; readers in `crates/sources/src/gpu.rs`). The display adapter (the one the screen is driven by) is always awake, so it is read directly each time: Intel from the actual clock speed and the share of time it was not in its idle state (RC6, the chip's deep-sleep state), AMD and other vendors from the kernel's load, video memory, temperature and power files. A second, discrete GPU (for example this laptop's NVIDIA chip) switches itself off when idle and any query, even `nvidia-smi`, wakes it and keeps it awake for about 20 seconds; polling it would stop it ever sleeping. For those the thread reads only the power state from `/sys/class/drm` (reading that never wakes it) and shows "Powered down" without numbers while it sleeps. Only when the chip is awake and the thread has not touched it for 30 seconds (so something else is using it) does it start measuring (NVIDIA through one `nvidia-smi -i` process reporting every 5 seconds, others through their kernel files); after three idle readings in a row it stops, so the chip can sleep again. Unknown values stay unavailable and are never drawn as zero. The `system`, `ram` and `gpu` graphs are "compact" charts: each shares the widget's height with the others (no scrolling, and they follow the widget when it is resized vertically), and has no time or legend row, only the range on the right edge. The height each chart gets is the room left after the widget's text lines and the gaps between all its lines, split between the charts and never below 34 pixels (`chart_share` in `crates/tray/src/layout.rs`, requirement SQ-44); before 2026-11-08 the gaps were left out, so a widget with several charts, such as a two-GPU system, came out taller than its box and clipped its first line. Percentages are drawn on a fixed 0 to 100 scale; temperature and clock use a range that follows the data but is never narrower than 20 °C or 500 MHz, so a steady value is not stretched into noise (requirement SQ-33). Every widget type, not only these, now measures the room that is left under its title and controls (the token widget's range buttons may wrap onto more lines) instead of assuming a fixed amount: charts, including the token chart, split that room and follow the widget's height, and long lists scroll inside it. For an Intel GPU the figure is labelled "Awake": without administrator rights only the share of time the chip was out of its idle state (RC6) can be read, not the work it did, and a desktop keeps it awake roughly half the time. A widget also adds a notice when its source is not fresh, or has malformed or deferred records, and "Waiting for source status" before any status exists. The sessions widget shows running, waiting and blocked sessions always, completed ones for one hour, others for 24 hours, unless its `history` option is `true`. `format_utc` prints times as `YYYY-MM-DD HH:MM UTC` without reading a clock. The tests in `crates/widgets/tests/models.rs` (requirements SQ-5, SQ-6, SQ-8, SQ-10, SQ-11) check, among others, that a missing quota is not shown as zero, that projects with the same folder name stay separate, that nested agents stay under their real parent and that dates at the extremes do not overflow.

**Accounts and platforms (requirements SQ-35 and SQ-36, 2026-11-06).** The tray is meant to be shared, so nothing in it names one person's accounts or one operating system. *Accounts:* besides the default Claude, Codex and GitHub sign-ins, the configuration (`sources.accounts` in `crates/core/src/config.rs`) can list any number of extra accounts, each a kind (`claude`, `codex` or `github`), a short name, and where that tool keeps its own login: the Claude or Codex home folder, or a `gh` configuration folder (the one `GH_CONFIG_DIR` names) with its list of repositories. Nothing secret is stored: Status Quo only reads what the tool itself saved, as before. An account is named `kind:name` (for example `claude:work`); that key is what a widget's provider, a token record, a session, a usage reading and a health entry carry, so two accounts never mix. One worker (`accounts()` in `crates/collector/src/workers.rs`) reads the usage of every Claude and Codex account in turn with its own retry delay (an extra Codex account runs `codex` with `CODEX_HOME` set), the GitHub worker reads each login with its own `GH_CONFIG_DIR`, and transcript discovery walks every account folder. The Add widget menu and a widget's settings list every account, and Customize has a "More accounts" section. A widget set to an account that does not exist shows "unknown", never another account's numbers. Hook events (the live session states) still describe the default accounts only, and resuming a session of an extra account opens the tool without that account's home folder: both are known limits. *Platforms:* the code that touches the operating system is kept apart. On Linux the tray still uses the layer-shell, X11 or window hosts; on Windows 10 and 11 it was at first an ordinary window and is, since version 0.1.4, a frameless window on the desktop background (see the paragraph on the compatibility layer below). The link between collector and panel is a private socket file on Unix and, on Windows, a loopback network port whose number and a random token sit in a file in the user's private folder: a client must send the token first, so another user of the machine cannot talk to the collector (`crates/collector/src/transport.rs`). State lives in `%LOCALAPPDATA%\status-quo` on Windows, the program is installed under the same folder and started at login by a hidden script in the Startup folder (`windows_files()` in `crates/desktop/src/install.rs`), and private-file permissions are no-ops there because the profile folders are already private (`sq_store::private`). CPU time and memory come from `GetSystemTimes` and `GlobalMemoryStatusEx` (`crates/sources/src/system.rs`), every GPU of any vendor from the Windows GPU performance counters (the same ones Task Manager shows: an adapter's load is its busiest engine type summed over all processes; the adapter list, names and video memory come from the DirectX entries in the registry; NVIDIA adapters are also matched to `nvidia-smi` for temperature and power; `crates/sources/src/gpu.rs`); the CPU temperature has no driver-free source on Windows and shows "Unavailable". Tools such as `codex` that npm installs as `.cmd` files are found on `PATH` (`program()` in `crates/sources/src/lib.rs`), and links and session resumes are opened without a shell, so characters in a link cannot start another command. The Windows build is compiled and tested in real Windows 10 and Windows 11 machines kept on the laptop by [[vm-lab]], and the workflow file has a Windows job for the same. Results of 2026-11-06: the whole test suite (28 test programs) passes on Windows 10 (LTSC 2021) and Windows 11 (24H2), the collector runs and answers `inspect` there through the token-checked port, and install, reinstall and uninstall work and keep the user's own assistant hooks. Running the tests found four Windows-only faults, all fixed: a folder cannot be flushed like a file after a rename, a recreated file keeps its old creation time (file identity now uses the volume and file index), the installer rejected its own record, and a session-resume test assumed a Linux path. The window opens through OpenGL, and through DirectX (wgpu) when the machine has no OpenGL 2 (virtual machines, remote sessions, old drivers); the test VMs have no graphics card at all, so the window itself was not seen on Windows: with a software OpenGL driver (Mesa) added to the Windows 11 VM the window did open and showed all widgets with the collector connected. That run also found two faults, both fixed: the collector crashed when the computer had been running for less than a minute, because Windows clocks cannot be set back before boot, and a folder that does not exist because a tool is not installed was reported as a failed watch. Such folders are now simply skipped. The GPU widget is now simply called GPU. GPU test with real Windows counters (2026-11-06): no GPU emulator exists that fills these counters, but Windows 10 and 11 both ship a software adapter ("Microsoft Basic Render Driver") that publishes the real `GPU Engine` and `GPU Adapter Memory` counters, so the test VMs exercise the real reading path. A live test in `crates/sources/src/gpu.rs` opens the counters, checks that the first sample only primes, and that every listed adapter reads 0 to 100; it passes on Windows 10 and 11 (10 of 10 GPU tests). It found a fault, now fixed: the DirectX registry keeps adapters from earlier boots (their LUID changes on every start), so a ghost adapter that never reads was listed; adapters are now kept only when the counters report them (`keep_live_adapters`), and all are kept when the counters report nothing. A real second GPU was not available to test; the VMs have one software adapter.


**Wallpaper colours (requirement SQ-37, 2026-11-06).** The option "Follow the wallpaper colours" in Customize (also available per widget, off by default; field `follow_wallpaper` of the theme in `crates/core/src/config.rs`, so older configuration files load with it off) makes the widgets use a palette built from the desktop wallpaper. Three parts do it. *Colours (`crates/core/src/wallpaper.rs`, package `sq-core`, pure):* `seed_from_pixels` weights every sampled pixel by how colourful it is and how far from black or white, groups them into 36 hue bins and returns the dominant hue; a greyscale picture gives no hue (chroma 0) and the palette then stays neutral instead of inventing one. `Palette::from_wallpaper(seed, dark)` builds the palette of the dark or light look from that hue and moves text to a contrast of at least 7:1 and the accent, muted, warning and error colours to at least 4.5:1 against the background (WCAG contrast ratio, a measure of readability). Mode System uses the desktop's own light or dark setting. *Finding the picture (`crates/sources/src/wallpaper.rs`, package `sq-sources`):* the file named by the environment variable `STATUS_QUO_WALLPAPER` wins; otherwise, on Linux, the readers are tried in the order of `XDG_CURRENT_DESKTOP` (a desktop named there goes first, so a leftover file of another desktop cannot win): KDE Plasma's `plasma-org.kde.plasma.desktop-appletsrc` (a wallpaper package folder resolves to its smallest picture), `gsettings` for GNOME and its relatives, Cinnamon and MATE (the `picture-uri-dark` key when the colour scheme is dark), `xfconf-query` for Xfce, the settings files of LXQt and LXDE, nitrogen and `~/.fehbg`, and `hyprpaper.conf`. On Windows it reads the registry value `WallPaper` through `reg query` (without a console window); when that value is empty (Windows shows a plain colour instead of a picture) it reads the colour from the registry value `Background` under `Control Panel\Colors` and the palette is built from that colour (since 2026-11-19, in the repository, not yet in a release); otherwise it falls back to `%APPDATA%\Microsoft\Windows\Themes\TranscodedWallpaper`. The picture is decoded with the `image` library (PNG, JPEG, BMP, WebP; at most 256 MiB and 30,000 pixels a side), shrunk to 64 pixels and reduced to the hue; formats it cannot read, such as JPEG XL, give an explicit reason. `crates/sources/examples/wallpaper_probe.rs` prints what this machine yields. *Keeping it current (`crates/desktop/src/wallpaper.rs`):* a thread of the desktop program looks every 30 seconds, only while some theme follows the wallpaper, and decodes again only when the file path or its change time differs. The tray (`Tray::effective_theme` in `crates/tray/src/ui.rs`) swaps in the wallpaper palette only when colours were reported; while they are pending or unavailable, the configured palette stays in use and Customize says why next to the option, and, while the wallpaper palette is active, the colour swatches show the colours in use (not editable) instead of the stored palette. The browser demonstration has no access to a wallpaper, so there the option shows as unavailable. Checked: tests for the colour maths (all hues, four saturation levels, both looks), the parsers and fixture desktops for every reader including the Windows ones, real PNG and JPEG decoding, and the tray rule (`REQ SQ-37` in `crates/core/tests`, `crates/sources/tests` and `crates/tray/tests/layout.rs`); on this laptop's KDE session the probe found the Orionids wallpaper, and a screenshot of the production program with the option on showed the accents change from green to indigo. Checked on 2026-11-19 with real runs: on Windows 10 and Windows 11 virtual machines from [[vm-lab]] the wallpaper was changed to a blue, a red and a multicoloured picture, an unreadable file and a plain colour, in the dark and in the light look, and each time the panel took a readable palette of that colour (the unreadable file kept the configured palette and Customize gave the reason); on Linux the release program was run on a hidden virtual KDE desktop with ten wallpapers in both looks. The same change keeps the accent colour away from the hues of the warning and error colours and makes the buttons of Customize dark or light according to the background that is actually drawn. Not checked: GNOME, Xfce, LXQt, feh, nitrogen and hyprpaper on a real desktop (fixtures only). Known limits: KDE's separate dark picture folder (`images_dark`) is not used, a Plasma slideshow or a Linux desktop with a solid colour gives no picture and so no colours, a grey picture with one small vivid spot gives a palette tinted with that spot, and a wallpaper changed by a program that does not write the desktop's settings is seen only through `STATUS_QUO_WALLPAPER`.

**Session progress and the folder navigator (requirements SQ-38 and SQ-39, 2026-11-06).** *Progress finds its own data.* The done/total count of a session ("2/5" in the sessions widget) used to come only from the files of the separate `codex-pbar` footer tool, and only for Codex. Now `LogParser` (`crates/sources/src/parse.rs`) rebuilds the task list from the session's own transcript, for Claude and Codex alike: Claude's `TaskCreate` adds a step, `TaskUpdate` changes its status (pending, in progress, completed) or deletes it, `TodoWrite` replaces the list; Codex's `update_plan` call replaces the list (this Codex format is written from the tool's documented shape and was not seen in this laptop's own Codex transcripts, so it is tested with a made-up line only). A transcript line repeated by streaming counts once, an unknown task id changes nothing, and a session without a list shows no count at all, never 0/0. The step marked in progress becomes the session's task label when none is known. The `codex-pbar` folder (`sources.progress`) is now an optional extra: it defaults to empty, a saved configuration that still holds the old default has it cleared when loaded (`crates/store/src/lib.rs`), progress files are used only for a session whose transcript has no list, and a missing folder is not a fault and adds no health notice. Because transcripts read before this change had no lists, the saved reading positions are reset once (state version 3 in `LocalState::upgrade`) so every transcript is read again from the start; Claude token records are deduplicated by identity and Codex token records are rebuilt, as in version 2. On this laptop the rebuilt snapshot showed a real Claude session with 3 of 3 steps and no progress health entry. *Folder navigator.* Next to each source path in Customize (Claude folder, Codex folder, workflow memory, the optional progress folder, the home folder of each extra account) a Browse button opens a window titled "Choose a folder" with a plain explanation, Home, Up and root buttons (`/` on Unix, the existing drives on Windows), the current path, the sub-folders as buttons (visible ones first, hidden ones such as `.claude` after) and "Use this folder" and Cancel; "Add a project folder…" does the same for the project roots. Nothing changes until Use. The tray has no file access (its package may not use the file system): the host implements the `FolderBrowser` trait (`Folders` in `crates/desktop/src/native.rs`, read-only listings), and without one, as in the browser demonstration, the Browse buttons are hidden. **Compatibility layer.** `crates/desktop/src/host/` is the only code that knows how the tray is placed on a given Linux desktop, and it chooses at run time, so one program works across distributions (decision in `docs/adr/0004-host-compatibility-layer.md`). Layer-shell, a Wayland protocol that lets a program draw on the desktop layer, is used when the compositor offers it (KDE Plasma, Hyprland, sway); the tray then has no frame, is anchored to an edge or corner (`STATUS_QUO_ANCHOR`, default top-right) and draws only when something changed. On an X11 session it uses a frameless window with window-manager hints for below, off the taskbar and off the pager; asking for all workspaces is best effort because KDE's X11 compatibility ignores it. Until version 0.1.3 everything else, for example GNOME on Wayland and Windows, fell back to an ordinary window. `STATUS_QUO_HOST=layer-shell|x11|window` forces a choice when it can work. In these two hosts the tray is bare: it has no background or title of its own, only the widgets and the three small buttons Add widget, Edit tray and Customize are visible (the connection status appears only while disconnected), and the rows of widgets are scaled so they fill the tray space exactly, with equal gaps. Customization and screenshots use the ordinary window because the layer host has no keyboard input yet.

**Desktop background everywhere, floating window as a setting (requirement SQ-48, version 0.1.4, 2026-11-18; amendment in `docs/adr/0004-host-compatibility-layer.md`).** Giovanni reported that the tray opened as a floating window on Windows; the decision is that the desktop background is the default on every system and the ordinary window is a user setting. `host::select` in `crates/desktop/src/host/mod.rs` now takes the `floating` field of the configuration (`crates/core/src/config.rs`, `false` by default, so settings saved before it existed load with it off). With it off, the host is layer-shell where the compositor offers it; the X11 host on an X11 session and, through XWayland (the part of a Wayland session that runs X11 programs), on Wayland without layer-shell such as GNOME, whose window manager Mutter accepts the same hints; and on Windows a new host, `windows-desktop` (`crates/desktop/src/host/windows.rs`): a window without frame and without a taskbar button, kept below the others. An ordinary window remains only where none of these is possible. With the setting on, the host is the ordinary window on every system. The host is fixed when the window is created, so changing the setting (the checkbox in Customize, or `status-quo floating on` and `off` from a terminal, handled in `crates/desktop/src/main.rs`) restarts the panel: on Linux the process replaces itself, so the login service keeps watching the same process; on Windows a new panel starts, waits for the panel lock and the old one closes. A frameless panel is moved by dragging the empty part of its top row, and the buttons of that row stay clickable. Windows brings a window to the front at every click, so the Windows host answers every reordering request with "bottom" while the layer is Behind; the Above and Normal layers lift that hold. A floating window treats the Behind layer as Normal on every system, because a titled window held behind could never be brought to the front. On Windows the first position (top right) and every restored position stay inside the free part of the screen, above the taskbar. Where Windows has no usable OpenGL the panel draws through DirectX, which cannot make the window see-through: the background is then solid and Customize says that Background opacity has no effect. That limit of version 0.1.4, the Windows *Show desktop* shortcut (Windows key with D) hiding the panel like any window, is removed in the repository since 2026-11-19 (not yet in a release): see the next paragraph. Tests tagged `REQ SQ-48` are in `crates/desktop/src/host/mod.rs` (host choice for each kind of session), `crates/desktop/src/native.rs`, `crates/core/tests/behavior.rs` and `crates/tray/tests/layout.rs`; the real runs on Mutter and on Windows are described on [[status-quo-install]]. Checked on 2026-11-18 in Windows 10 and Windows 11 virtual machines from [[vm-lab]]: the installed panel is frameless at the top right above the taskbar and stays behind a terminal window, and on Windows 11 the *Show desktop* shortcut hid it and a second press brought it back. Not checked: the see-through background on Windows (the virtual machines have no OpenGL) and the 0.1.4 program on the laptop's physical screen.

**The Windows panel as part of the desktop (requirements SQ-48 reworded, SQ-49, SQ-50; 2026-11-19, released in version 0.1.5).** Giovanni reported that on Windows the 0.1.4 panel still behaved like a floating window. `crates/desktop/src/host/windows.rs` now makes it a "tool window" (a window style that Windows leaves out of the taskbar and out of the Alt+Tab window switcher) that is owned by the desktop while the layer is Behind. An owned window is always stacked directly in front of its owner, so *Show desktop*, which minimises ordinary windows, leaves the panel in place, and a second press brings the other windows back. "The desktop" is the window that holds the desktop icons at that moment: normally the window named "Program Manager"; on Windows 10, *Show desktop* moves the icons into a separate full-screen window in front of all others, which covered the panel, so the function `icon_host` picks the owner again whenever another window becomes active, is minimised or is restored, and once per drawn frame (found on Windows 10 LTSC 2021; Windows 11 keeps the icons where they are). "Behind the other windows" therefore means "directly in front of the desktop" (function `stack_place`): the bottom of the stack normally, and the place right in front of that raised window while *Show desktop* is on, so a window opened in that state still comes in front of the panel. A click never makes the panel the active window; it takes the keyboard only while a text field of the panel that was just clicked is being typed in, and gives it back afterwards. When Windows Explorer (the program that draws the desktop and taskbar) restarts, the panel attaches to the new desktop. SQ-49: the panel and the collector no longer depend on the terminal that started them, so closing that terminal leaves the panel running. SQ-50: the saved place is the position of the whole window, so a floating window no longer moves down and right by the height of its title bar at every start, and a saved place outside the screen is moved inside it. Checked on 2026-11-19 with real runs on Windows 10 and Windows 11 virtual machines from [[vm-lab]] (1280x800, drawn without a graphics card): the install test of [[status-quo-install]] passed on both; the stress script `tools/stress/windows.ps1` (real clicks, keys and restarts: every layer with and without the Floating window setting, *Show desktop* 15 times, twelve windows over the panel, 300 clicks, Explorer restarts, three idle minutes) gave 103 passed and 0 failed checks on each (105 on Windows 10 after a round was added for a panel started while *Show desktop* is on), with memory steady at about 50 MB; eight presses of Alt+Tab never reached the panel. Not checked: a screen smaller than the panel, a screen resolution changed while the panel runs, the see-through background on Windows, and a computer with a real graphics card. The script is run by hand before a release (`docs/MAINTENANCE.md`, section 8); it is not part of CI (continuous integration, the checks GitHub runs on every push).

**See-through on Windows without OpenGL (requirement SQ-52, 2026-11-19).** egui is the interface library the panel is drawn with; wgpu is the graphics library under it that talks to DirectX, the Windows graphics system. On a Windows computer without usable OpenGL (another graphics system; missing in virtual machines, remote sessions and with old drivers) the panel used to fall back to DirectX through wgpu 24, whose picture buffer is made straight from the window and cannot be see-through, so the panel was drawn with a solid background. Giovanni allowed a library upgrade: egui and eframe went from 0.31 to 0.33 and wgpu from 24 to 27, which needs Rust 1.88. wgpu 27 can show its picture through DirectComposition, a Windows service that lays pictures with transparency over the desktop. `crates/desktop/src/main.rs` asks for it by setting the environment variable `WGPU_DX12_PRESENTATION_SYSTEM` to `DxgiFromVisual` when nobody has set it (wgpu 27 reads the choice there and does not export the type that names it), and the function `see_through_possible` decides from the graphics adapter's list of alpha modes (ways of mixing a picture with what is behind it): with premultiplied or postmultiplied alpha the panel is see-through, otherwise it stays solid and Customize says so. Checked on 2026-11-19 on the Windows 10 and Windows 11 virtual machines from [[vm-lab]], which have only Microsoft's software renderer: the panel log said `alpha modes [Auto, Inherit, Opaque, PostMultiplied, PreMultiplied], see-through: true`, a red wallpaper showed between the widgets on screenshots, and the stress script gave 105 passed and 0 failed checks on each. On Linux, screenshots on a hidden KDE desktop showed the same layout, with text about 5% wider from egui's newer text drawing. Not checked: a Windows computer with a real graphics card.

**Linux layer-shell renderer fixed (2026-11-19, version 0.1.6).** The library upgrade above broke the Linux panel on every desktop that offers layer-shell (KDE Plasma on Wayland, sway, Hyprland): version 0.1.5 stopped at start with "No wgpu backend feature that is implemented for the target platform was enabled". Up to wgpu 24, the Vulkan and OpenGL ES backends (the two ways wgpu draws on Linux) were always built in; since wgpu 25 they must be named as features, and `crates/desktop/Cargo.toml` named only `wgsl`. It now names `vulkan` and `gles`, and a test tagged `REQ SQ-26` in `crates/desktop/src/host/layer.rs` (`the_layer_shell_renderer_has_vulkan_and_opengl`) fails without them. CI (continuous integration, the checks GitHub runs on every push) did not see the crash because its Linux runs used X11 and GNOME, which do not use the layer-shell renderer; the job `linux-layer-shell` now draws the real panel on sway (see [[status-quo-install]]). Found on 2026-11-19 while testing the self-update below on a virtual KWin screen (KWin is the KDE window manager).

**Updates through GitHub (requirements SQ-53 and SQ-54, `docs/adr/0007-updates-through-github.md`, 2026-11-19, from version 0.1.6).** Giovanni asked that every installed tray and the project's dependencies update themselves through GitHub when something new is there. Two parts:

- *The repository updates itself (SQ-53).* The workflow `.github/workflows/update-dependencies.yml` runs every Monday at 04:17 UTC and on demand. `tools/update_dependencies.sh` moves `rust-toolchain.toml` (the file that names the Rust release every build uses) to the newest stable Rust, runs `cargo update` (newest library versions that the version ranges in `Cargo.toml` allow and that still build with the oldest supported Rust, `rust-version` 1.88), takes the newest release of the shared checker `pipeline-check`, and the newest digests of the two manylinux build images listed in `tools/build-images`. When the shipped program can change, it raises the patch version. The workflow commits that to a short-lived branch, starts the full CI (`quality-gate.yml`, including the real install tests) on exactly that commit, and only when it passed pushes the same commit to `main` and, with a new version, pushes the tag and starts `release.yml`. A failure, or library versions that need a change of `Cargo.toml`, is written to a GitHub issue. The pinned GitHub actions cannot be updated this way, because the key a workflow gets from GitHub may not change workflow files: GitHub's Dependabot proposes them weekly (`.github/dependabot.yml`), and `dependabot-merge.yml` turns on auto-merge, which merges only after the required checks passed.
- *Installed trays update themselves (SQ-54).* `crates/desktop/src/update.rs`: three minutes after the panel starts, and then every six hours, the installed program (never a copy started from a source folder) reads `version.txt` of the newest GitHub release. If that version is higher, it downloads the file for its system, refuses it unless its SHA-256 checksum (Secure Hash Algorithm 256, a fingerprint of the file) equals the published `.sha256` file, and runs that release's own installer: `status-quo-setup.exe --yes` on Windows, the package's `install.sh --no-deps` on Linux (through `systemd-run` when the panel is a systemd service, so the installer survives the panel's restart). Settings, layouts, history and hooks stay. The checkbox *Update automatically* in Customize (on by default) turns it off; `status-quo update` installs at once and `status-quo update --check` only reports; `update.log` in the state folder records each attempt. `release.yml` publishes `version.txt` last, only after the published downloads passed their install tests, so a tray is only offered a release that installed on bare machines.

Checked before the release on 2026-11-19: on Linux in a bubblewrap sandbox (an isolated copy of the system with its own process list, an empty home folder, no systemd and a virtual KWin screen) and on the Windows 11 virtual machine from [[vm-lab]], an installed 0.1.6 panel found a 0.1.7 build in a local release folder, downloaded and checked it, installed it and restarted with it (Windows: after about 25 seconds with the first wait shortened to 20 seconds; the panel was seen on the desktop afterwards).

**Edit tray (requirement SQ-29, redesigned 2026-11-02, decision in `docs/adr/0005-free-canvas-layout.md`).** The Edit tray button turns the tray into a free canvas editor that works with the pointer alone. Each widget can carry an explicit rectangle in pixels (`x`, `y`, `width`, `height`, in `crates/core/src/config.rs`); a width of 0 keeps the old flow of rows, so old configurations load unchanged, and the validator accepts widths of 120 to 8000 and heights of 60 to 8000. Pressing Edit tray first freezes what is on screen into rectangles, so nothing jumps (`freeze` in `crates/tray/src/layout.rs`). Then every border and corner of a widget resizes it on both axes to any size, and dragging the body moves it anywhere (`drag_rect`, which keeps a minimum size and never crosses the canvas corner). Widget content is switched off while editing so it cannot take the pointer from the handles. All changes happen on a draft copy: Done normalizes the canvas to its corner, records the corner's desktop position in the saved `tray` geometry and saves through the same validated configuration path as Customize; Cancel discards the draft. Widgets learn how much room they have: charts take about 55 percent of the widget height, and token controls and meter text wrap (`crates/tray/src/ui.rs`). Outside editing, the tray reports the size it wants (`desired_size`: the canvas from `free_rects` and `canvas_size`, plus the header), and the layer-shell host sizes its surface to match (`Surface` in `crates/desktop/src/host/layer.rs`, chosen by `LayerApp` in `crates/desktop/src/main.rs`): `Legacy` is the first-run corner layout, `Free` docks the surface at the saved desktop position, and `Editing` covers the whole output, transparent and above windows, so a widget can be dragged anywhere. Window hosts follow with an inner-size request instead. The docked surface is kept on the screen: `clamp_to_screen` in `layer.rs` slides a tray that a widget move made too wide or too low back inside the output, and `docked_origin` reports the clamped corner, so the header buttons stay reachable. Overlapping widgets are allowed; the tray draws each free widget in its own egui layer (an `Area`), stacked in configuration order, so the widget on top also receives the pointer where widgets overlap (test `a_button_on_the_top_widget_still_works_where_widgets_overlap` in `crates/tray/tests/layout.rs`). Only the first output is used (per-monitor placement is not handled). Checked so far: tests drive real pointer events through the tray, and an isolated run in a real compositor rendered a docked free layout correctly (both as recorded in ADR-0005, the architecture decision record (ADR) of this change; the run itself was not repeated here). A drag in the full-screen editor on the real desktop, driven with a virtual mouse by the desktop end-to-end test, was first run on 2026-11-04 (see the paragraph on desktop-wide placement below). The effect of the redesign on the idle CPU use is not measured. The change is committed on the branch `feature/free-canvas-edit-tray` (855ffd7, then f7f88de and 13e05e8 on 2026-11-04) and pushed to the remote; the continuous integration (CI) job `gate` passed on 13e05e8 (run 41943440329); the branch was fast-forwarded into `main` on 2026-11-04 (`origin/main` is now 13e05e8); the branch was then deleted.

**One gap and sticky borders (SQ-29, update of 2026-11-02 in ADR-0005).** `Config.gap` in `crates/core/src/config.rs` is the single space between widgets, in pixels: 0 to 64 (the validator rejects other values), default 10. The flow layout, the stacking of widgets without a rectangle and the editor all use it. In Customize the slider "Space between widgets" sets it; that slider in `crates/tray/src/ui.rs` runs only from 0 to 40, so 40 to 64 can come only from a configuration file (read from the code, not run). While editing, `layout::snap_rect` makes a dragged border stick to other widgets within 10 pixels (`SNAP` in `crates/tray/src/layout.rs`): a border settles exactly one gap from a neighbour's border, or flush with an aligned border, and a width or height near another widget's becomes exactly that size; gap and alignment win over size when both are near. The tray keeps the unsnapped rectangle that follows the pointer and draws the snapped one, so a widget that stuck lets go again when pulled further. The Edit tray button is disabled while Lock widget layout is on (its tooltip says to unlock in Customize). A widget added to a tray that already has explicit rectangles gets one at the top-left corner (x and y 0, width 420 pixels), so it is visible and can be dragged. When editing starts, a first-run layout taller than the space the tray had is compressed vertically to fit (`fit_to_space` in `ui.rs`). Alignment guides (requirement SQ-34, `guides()` and `snap_rect()` in `layout.rs`, painted by `paint_guides()` in `ui.rs`): while a widget is dragged, the tray draws a pink line where one of its borders lines up with another widget's border (flush, or one gap apart), a dashed blue line where their centre axes coincide, and an amber bar under (width) or beside (height) both widgets when they have the same size. All of these are sticky points within 10 pixels, tried in the order borders, centres, sizes; a candidate that would make the widget smaller than the minimum or push it off the canvas is not offered, so every position the widget sticks at has a line that explains it. The lines disappear when the mouse is released. A random test of 6,000 drags checks these properties. Unit tests cover the snapping (inside `layout.rs`, and in `crates/tray/tests/layout.rs` a border that sticks at the gap and lets go, a size that sticks, the lock, the compressed first freeze) and the configuration limits and new-widget rectangle (`crates/core/tests/behavior.rs`). The new sticky step of the end-to-end test has NOT been run on the desktop: the run was withheld because the screen was in use, so the 22-check result below predates it and shows nothing about snapping on the real desktop.

**Desktop-wide placement and Remove (SQ-29, update of 2026-11-04 in ADR-0005).** Two changes to Edit tray. First, widgets can now be placed anywhere on the desktop. Before, the full-screen editor measured every widget from the docked tray's top-left corner and stopped it at zero, so a widget could not be dragged left of or above that corner. Now `Tray::set_origin` in `crates/tray/src/ui.rs` shifts each draft widget once by the tray's desktop position when the host reports it (the host reports it after `begin_edit`, just before the surface covers the desktop; an earlier version shifted inside `begin_edit`, too early, and drew every widget at the left edge), so a position is a desktop position (still not below zero, and not above the header height, because the docked tray needs its header above the widgets); Done saves the position of the leftmost and topmost widget as the tray's desktop position (`normalize_canvas`). Window hosts are unchanged. Second, every widget in the editor shows a "Remove" button at its centre (`edit_handles` in `ui.rs`, added after the resize handles so it receives the pointer before the body drag). Pressing it removes the widget from the draft only: Done saves the smaller tray and Cancel brings the widget back. Because the centre now holds the button, dragging a widget by its body must start away from the centre; the tests and the end-to-end test do so. Tests in `crates/tray/tests/layout.rs`: `a_remove_button_in_the_widget_centre_removes_it_from_the_draft_and_cancel_restores_it`, `removing_a_widget_and_pressing_done_saves_the_smaller_tray` and `a_full_desktop_editor_places_widgets_left_of_and_above_the_docked_tray`; the gate passed. Checked on the real compositor on 2026-11-04 with the desktop end-to-end test (new step 8c: move the topmost widget far left of the docked tray, Remove then Cancel, Remove then Done), run with `STATUS_QUO_E2E_EMPTY_HOME=1`, which starts the private copy with an empty home folder because its cold read of every real transcript kept it busy for minutes and starved the virtual mouse (the idle CPU of such a run says nothing about the real load): 28 of 29 checks passed. The sticky-border step still fails (60.4 against 10 pixels, with overlapping widgets on screen) and is open; it had never been run on the desktop before.

## Engineering practices
How this project follows the golden path of [[project-template]].

### Principles
1. **Requirements precede changes**: tests carry a standalone `// REQ SQ-n` comment, and the traceability step ([[check-traceability]]) fails when a requirement has none.
2. **Portable packages stay free of input and output**: core, contract and widgets, checked by a project-specific detector with planted-defect self-tests.
3. **Everything is a removable widget**: no permanent provider slots in the tray.
4. **The gate decides**: `tools/quality_gate.sh` is the only definition of passing, and no limit is lowered to make it pass.
5. **Nothing private is stored**: no credentials, conversations or memory contents in fixtures, diagnostics or the browser demo.

### Decisions
`DESIGN.md` holds the architecture diagram and a dated decision log with the type of each decision. Seven architecture decision records (ADRs, short notes that keep the reasons for a decision) are in `docs/adr/`: 0007 updates through GitHub (2026-11-19, the paragraph above on updates), 0001 record decisions, 0002 portable Rust widgets, 0003 the program measures and the skill judges, 0004 the host compatibility layer, 0006 installers proven on bare machines (2026-11-18, see [[status-quo-install]]), and 0005 the free canvas layout (2026-11-02, a corrective decision by Giovanni: any widget size and position, and a tray surface that follows its widgets; it amends the tray rows of ADR-0002 and the fixed surface of ADR-0004). ADR-0004 carries an amendment of 2026-11-18 for the desktop-background default (SQ-48). ADR-0005 is committed in 855ffd7 and has an update section of 2026-11-02 (one gap, sticky borders, lock, new widgets, the docked tray kept on the screen and the exit flag polled every 200 ms); `DESIGN.md` has matching decision-log rows. `docs/adr/0000-template.md` is the blank form for the next one (status, date, type, who decided, context, decision, alternatives, consequences) and `docs/adr/README.md` is the index; a decided ADR is never rewritten, a new one replaces it. The approved scope is kept in `docs/2026-11-01-status-quo-design.md`.

### Requirements
54 requirements (prefix SQ, SQ-1 to SQ-54) in `docs/REQUIREMENTS.md` on 2026-11-19; the traceability step of the gate fails when one has no tagged test. There were 29, all covered by tagged tests, on 2026-11-02 (the wording of SQ-29 was replaced on 2026-11-02 for the free canvas and then extended with the single gap, the sticky borders and the layout lock; committed in 855ffd7). `docs/TRACEABILITY.md` is the table the traceability step generates: each requirement with the test files that carry its tag; it is not edited by hand. A tag proves a test exists, not that the real desktop behaves correctly.

### Quality gate
Five steps: formatting (followed since 2026-11-07 by step 1b, which refuses a test folder made outside `crates/scratch.rs`; [[tmp-junk]]), compiler diagnostics with warnings denied plus all tests, the Rust boundary check (which also self-tests `tools/resource_check.rs`; followed since version 0.1.3 by step 3b, which checks with `tools/check_binary.rs` that the built program is linked only against the C library), requirement traceability (the step fails when the regenerated `docs/TRACEABILITY.md` differs from the committed one) and the 1200-second gate-duration limit. An optional sixth step, the desktop end-to-end test, runs only when `STATUS_QUO_E2E=1` is set ([[checks-status-quo]]). `tools/resource_check.rs` measures the real processes over five minutes. The first observation met the memory target (115 MiB of 200 MiB) and missed idle CPU (2.05% of one core against 1%).

### Continuous integration
Continuous integration (CI) means automatic checks on every push. `quality-gate.yml` installs the Rust release named in `rust-toolchain.toml` (1.88.0 on 2026-11-19; 1.87 before the egui upgrade; the weekly update workflow moves it to the newest stable release), runs `pipeline-check --mode ci` pinned in `pipeline-check.version` (v0.8.0 since 2026-11-07; before v0.5.0 and v0.4.0), and builds the browser version; a second job, `windows`, builds and tests the workspace and the installer on Windows. Since 2026-11-06 `main` requires both jobs (and since 2026-11-18 also `packages / install-proof`, the real installs described on [[status-quo-install]]); `windows` had been red from commit b701cda to 5d47999 because a new test made Unix-only assumptions while only `gate` was required (details on [[checks-status-quo]]). No run for commit 855ffd7 appeared in `gh run list` on 2026-11-02, so that commit has not been through CI.

### Maintenance
`docs/MAINTENANCE.md` states the method: debt is a GitHub issue labelled `debt` (P1 to P3) and `idea` for features, about one session in five goes to debt or prevention, and a monthly review of every project records a Preventive decision-log row. It follows the template's file and adds that the required CI check `gate` must pass on the exact commit before promotion to `main`. Technical debt belongs in GitHub issues labelled `debt` under the [[maintenance-policy]], and the [[monthly-architecture-review]] checks the project. Branch protection cannot be enabled on a private repository on the free GitHub plan.

## Notes
Build with `cargo build --release --locked -p status-quo`; the installer is `status-quo install` and `status-quo uninstall` reverses it. State lives in `~/.local/state/status-quo`; `STATUS_QUO_STATE_DIR` redirects it for tests. On the laptop, test runs on 2026-11-02 showed the layer-shell host with live data, the collector seeing real assistant sessions through the hooks, a mouse click changing a widget, and a 60-second idle measurement of 1.08% of one core and 195 MB combined (the graphics driver libraries account for most of the panel's 156 MB). `docs/TESTES-AUTOMATIZADOS.md` (in Portuguese, as its name says) is the record of the bug-finding tests; see [[checks-status-quo]]. Not yet observed: login startup, the 100 ms interaction limit, the full five-minute run, keyboard input in the layer host, GNOME or any other desktop than KDE Plasma, and a real X11 session. The cause of the remaining idle CPU use is open.

**Transcript discovery (requirement SQ-31).** The collector finds Claude and Codex transcript files by walking their folders and reading at most five levels. Only files count toward the 100,000-file safety bound; empty folders do not. A projects folder once held about 94,000 empty folders left by throwaway working directories, which made the old scan fail every time (token history stopped updating) and made the collector watch about 190,000 folders, nearly the system limit for file watches (inotify). Now only Claude project folders holding recent transcripts are watched (about 580 watches), plus the projects folder itself to notice new projects within 30 seconds. Two tools added on 2026-11-06 support later speed work. The test `repeated_discovery_matches_a_fresh_walk` in `crates/sources/tests/adapters.rs` checks that discovering transcripts again and again finds exactly what one fresh walk finds (a transcript added to an unchanged folder, a folder removed, a transcript becoming too old, the depth limit, a subagent's parent session); it guards any future caching of folder listings in `LocalState::discover`. The example program `crates/sources/examples/local_bench.rs` (run with `cargo run --release -p sq-sources --example local_bench`) times one "local" round of the collector against the real folders: discovery, a full read, a read of a few changed files, token buckets, pruning and saving the checkpoint (the collector's saved reading position). It only reads, and prints timings and counts, never transcript content; it was written to find where the collector spends processor time while idle.

**Desktop end-to-end test.** This test exercises the real tray on the real desktop, which the ordinary tests cannot do. `tools/ui_e2e.sh` builds the production program and runs `crates/desktop/tests/desktop_e2e.rs`, a Rust test marked ignored so that a plain `cargo test` skips it. The test pauses the live tray, starts a private copy with its own state folder and collector, and drives it with a virtual mouse created through `/dev/uinput` (the Linux interface for fake input devices). It then reads what the tray saved in its configuration and checks it. It covers: start, idle CPU and memory, Edit tray and Cancel, moving a widget, resizing by a corner and by an edge, Done and docking, the token controls, Add widget, Customize and Cancel, and a restart. Afterwards it restarts the live tray.

**Run it:** `tools/ui_e2e.sh` from the repository root, or `STATUS_QUO_E2E=1 tools/quality_gate.sh` to run it as optional gate step 6. **Needs:** a Wayland session, a writable `/dev/uinput` and the screenshot program `spectacle`; without one of them the script prints "skipped" with the reason and exits successfully, so a skip is not a pass. **Refuses unless the screen is free:** without `STATUS_QUO_E2E_SCREEN_IS_FREE=1` the script prints a refusal and exits with status 2, because the virtual mouse clicks for about three minutes on whatever window is in front, and one run once clicked into a maximized browser. Close or minimize windows over the right side of the screen and keep hands off the mouse first (`docs/MAINTENANCE.md` section 7); optional gate step 6 therefore needs both `STATUS_QUO_E2E=1` and this variable. **Output:** `build/e2e/report.json` (each check with `ok` and a detail, a `data` block, and the open findings) and screenshots `build/e2e/*.png`. The expected positions and numbers come from a manual test of 2026-11-02, saved in `crates/desktop/tests/e2e/manual-baseline.json`; `docs/MAINTENANCE.md` section 7 says to repeat the manual pass, update that file and extend the test whenever a major tray update lands.

**Result of the real run on 2026-11-02:** 22 checks passed (read from `build/e2e/report.json`, a generated file that is not in git). Idle CPU for panel plus collector was 1.30% of one core over 20 seconds, and memory 182 MiB (limit 200 MiB). The 1% target of requirement SQ-23 is still missed: the test gates only on a 2% ceiling and records the target result (`meets_sq23_cpu_target_over_20s: false`) as data. The test drove three fixes: the docked tray falling off the screen after a move, the unclamped editing origin, and clicks lost where widgets overlap (decision-log row of 2026-11-02 in `DESIGN.md`).

**Findings.** The four findings of the first run (Edit tray ignoring the layout lock, a new widget in a docked free tray landing below the canvas, the stop signal noticed only about 2 seconds late, and a first-run tray taller than the screen keeping widgets below its edge) are resolved in commit 855ffd7 (lock check, top-left rectangle for new widgets, exit flag polled every 200 ms, compression on freeze; `DESIGN.md` decision-log row of 2026-11-02). They are covered by unit tests; the desktop run was repeated on 2026-11-04 (28 of 29 checks passed; see the paragraph on desktop-wide placement). The baseline file now lists under `open_findings` only the idle CPU gap of SQ-23 (about 1.3% of one core against 1%, cause not found), copied into every report.

**Limits:** one screen size (1920x1080) and the first monitor; button positions are recorded values, not found on screen; the idle check lasts 20 seconds, not the 5 minutes of SQ-23. The test files are committed in 855ffd7.

**Browser demonstration (`docs/browser-demo.md`, `tools/build-web.rs`).** The package `sq-web` runs the same `sq-tray` interface in a browser with invented data, labelled as a demonstration. It does not connect to the collector or read credentials, transcripts, GitHub or workflow-memory, changes do not reach the desktop settings, and reloading restores the sample. It also registers an unrelated example build-status widget through the public widget contract, to show that no built-in provider slot is needed. `tools/build-web.rs` is a standalone Rust program, compiled with `rustc tools/build-web.rs -o /tmp/status-quo-build-web` and run from the repository root. It builds `sq-web` in release mode for the `wasm32-unknown-unknown` target (WebAssembly, the format browsers run) with `--locked`, runs `wasm-bindgen` (the tool that generates the JavaScript that loads the WebAssembly module; its version must match `Cargo.lock`) into `dist/web/pkg`, and copies `crates/web/site/index.html` to `dist/web`. With `--serve` it instead serves `dist/web` at `http://127.0.0.1:8765/` on localhost only, answers GET requests only and refuses paths containing `..`, `.`, `%` or a backslash. The variables `CARGO`, `CARGO_TARGET_DIR` and `WASM_BINDGEN` choose the tools; it never downloads any. The page needs a browser with WebAssembly and WebGL2 (a graphics interface) and must be opened through the server, not as a `file://` address. The document records one real-browser check of 2026-11-02 (open Customize, choose Light, Save changes) and three Rust tests of the browser host; this page's review did not repeat them (not verified now). Browser rendering does not establish desktop compositor, native socket, startup or source-adapter behavior.
