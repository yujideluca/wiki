## What it is
These are the checkers of the repository `status-quo` (see [[status-quo-design]] and [[status-quo-layout]]), a Rust workspace started from [[project-template]]. It lives in the public GitHub repository `yujideluca/status-quo` (MIT licence, since 2026-11-06). The continuous integration (CI) workflow `quality-gate.yml` has two jobs: `gate` (on Linux) and `windows` (builds and tests the whole workspace and the installer on Windows). Since 2026-11-06 `main` requires both. Before that only `gate` was required, so `windows` stayed red from commit b701cda without blocking anything: the new test `repeated_discovery_matches_a_fresh_walk` in `crates/sources/tests/adapters.rs`, checked only on Linux, made three Unix assumptions. It opened folders with a plain `File::open` to change their time, which Windows refuses ("Access is denied"); and it built the paths it looked up as `root.join(".claude/projects")`, whose string keeps a `/` while discovery stores Windows `\` paths, so the lookup found nothing. A `set_modified` helper in the test now opens files and folders with the Windows flags (`FILE_FLAG_BACKUP_SEMANTICS`, `FILE_WRITE_ATTRIBUTES`), and the paths are joined one part at a time. Both jobs passed on 5d47999 (2026-11-06), and `docs/MAINTENANCE.md` now says protection must require every CI job that checks a requirement. Since the repository became public, branch protection is on for `main`: the checks `gate` and `windows` are required, force-push and deletion are refused, and administrators are not forced (same as the wiki repository); the `protecao-de-branch` check of `pipeline-check` reported OK on 2026-11-06. Changes go to a short-lived `ci/sq-NN` branch first, and `main` is pushed only after both jobs are green on that exact commit. All workflow actions are pinned to commit hashes (SQ-43), and the installer and release workflow are described on [[status-quo-install]].

## What it does
The gate (`tools/quality_gate.sh`) runs five steps in order: Rust formatting (`cargo fmt --check`), followed since 2026-11-07 by step 1b, which fails when a test builds its own temporary folder (every test folder must come from `Scratch` in `crates/scratch.rs`, shared by all crates and removed when the test ends, also when it fails; any other `temp_dir()` line must say `scratch-ok:` and why; see [[tmp-junk]]), compiler diagnostics with warnings denied (clippy) plus the whole test suite, a project-specific boundary check (`tools/rust_architecture.rs`, which also self-tests `tools/resource_check.rs`), requirement traceability (it also fails when the regenerated `docs/TRACEABILITY.md` differs from the committed copy), and the fitness limit on gate duration (1200 seconds). The CI run of the latest pushed commit (d285287 on `main`, run 42263090750) passed on both of its jobs: `gate` on Linux and `windows`, which builds the workspace and runs its tests on a Windows machine; the local gate also passed on the same tree. The tutorial is checked inside the test suite by `crates/desktop/tests/docs.rs` (requirement SQ-40): relative links resolve, and every widget and `STATUS_QUO_*` variable it names exists.

An optional sixth step runs only when the variable `STATUS_QUO_E2E=1` is set: `tools/ui_e2e.sh`, the desktop end-to-end test of the real tray (it pauses the live tray, drives a private copy with a virtual mouse and writes `build/e2e/report.json`). It is optional because it needs a Wayland session, a writable `/dev/uinput` and `spectacle`, so a normal run and the continuous integration (CI) run (which has no desktop) leave it out; the script itself skips with a stated reason when a need is missing. The test is not part of the five-step definition of passing: it complements the gate by checking what no unit test can, and `docs/MAINTENANCE.md` section 7 asks for it before closing a major tray update and before a release. A real run on 2026-11-02 passed 22 checks. The script now refuses to run (exit status 2) unless `STATUS_QUO_E2E_SCREEN_IS_FREE=1` is set, because the virtual mouse clicks on whatever window is in front and one run once clicked into a maximized browser (`docs/MAINTENANCE.md` section 7); with `STATUS_QUO_E2E=1` alone the optional gate step 6 therefore stops. The test gained a step for the sticky borders of the free canvas. It was first run on the desktop on 2026-11-04, with the private copy started on an empty home folder (`STATUS_QUO_E2E_EMPTY_HOME=1`), and it fails: 60.4 against 10 pixels, with overlapping widgets on screen. That run passed 28 of 29 checks; both facts are read from `docs/adr/0005-free-canvas-layout.md` and were not repeated in this review. Its idle CPU gate is a 2% ceiling, while the 1% target of SQ-23 (the idle-cost requirement) is recorded as data and still missed (1.30% of one core). Details: [[status-quo]].

The boundary check exists because the shared checker (`pipeline-check`, pinned at v0.8.0 since 2026-11-07) only scans Java and Kotlin. It rejects graphical, file, process or network dependencies in the three portable packages, allows only the egui interface library in the reusable tray, and has its own self-tests that plant defects and require them to be rejected. All 44 requirements (SQ group, SQ-1 to SQ-44) in `docs/REQUIREMENTS.md` have a test tagged with a standalone `// REQ SQ-n` comment; the scan covers `.rs` files under `crates` and `tools`. The wording of SQ-29 was replaced on 2026-11-02 (Edit tray as a free canvas, decision ADR-0005 (architecture decision record), see [[status-quo]]); its tag is in `crates/core/tests/behavior.rs`, `crates/tray/src/layout.rs`, `crates/tray/tests/layout.rs`, `crates/desktop/src/host/layer.rs` and `crates/desktop/tests/desktop_e2e.rs`, and `docs/TRACEABILITY.md` lists `behavior.rs, desktop_e2e.rs, layer.rs, layout.rs` for it. The gate was not run for this page update. A tag proves a test exists, not that the real desktop behaves correctly, so window stacking, login startup and the resource limits need separate observation (idle CPU was 2.05% of one core in the first five-minute run, 1.08% over 60 seconds and 1.30% over 20 seconds in later runs, against a 1% target).

## How it does it
CI (continuous integration) uses the standard workflow (`pipeline-check --mode ci`, 60 minutes at most) and adds a browser build for the `wasm32` target. `pipeline-check.toml` names the project, points at the repository `yujideluca/status-quo`, requires the check called `gate` on `main`, and lists `tools/hooks/pre-push` for the shell checker. Five ADRs (architecture decision records) exist, plus a blank template `docs/adr/0000-template.md`: 0001 (record decisions), 0002 (portable Rust widgets), 0003 (the program measures, the skill judges), 0004 (host compatibility layer) and 0005 (free canvas layout, committed in 855ffd7 on the branch `feature/free-canvas-edit-tray`). ADR-0001 says that structural decisions get an ADR in the same commit as the change, with `DESIGN.md` keeping the one-line log; the rejected alternative was a decision log alone, which loses the alternatives and which decision replaced which. ADR-0003 (2026-10-24, preventive) splits the work in two pieces that talk only through the file `report.json`: the program `pipeline-check` measures and blocks (it runs in CI without Claude and exits non-zero when a check is `falha`, with limits in `pipeline-check.toml` decided by Giovanni), and the skill `revisao-manutencao` reads that report, never measures, and proposes debt issues and a Preventive decision-log row for Giovanni to decide. Its update says the program is not copied into projects but lives in the repository `yujideluca/pipeline-check`, pinned by tag in `pipeline-check.version`. The host ADR is 0004; the Stop hook once named a file `0003-host-compatibility-layer.md`, which does not exist.

Three documents in `docs/` support the checks. `TRACEABILITY.md` is generated by `pipeline-check --traceability`: one row per requirement with the test files that carry its tag (for example SQ-8 lists `lifecycle.rs`, `models.rs`, `workers.rs`). `TESTES-AUTOMATIZADOS.md`, written in Portuguese, is the record of the bug-finding tests: a table of risks (configuration, contract, view models in `crates/widgets/tests/models.rs`, persistence, sources, transport, tray, boundary checker, browser reuse) against the test file and the behavior it must show, then the first five-minute resource runs (2.05% of one core, 115 MiB) and the host compatibility observations. It states that no coverage percentage or mutation score has been recorded; the only mutation-style evidence is a planted-defect run of the boundary checker. `MAINTENANCE.md` holds the debt, monthly review and `pipeline-check` method of the template.

Two scripts connect the repository to `pipeline-check`. `tools/pipeline-check.sh` reads the tag in `pipeline-check.version`, builds that version once into `~/.cache/pipeline-check/<tag>` (a shallow clone of `https://github.com/yujideluca/pipeline-check` followed by `cargo build --release`) and runs it with the given arguments: none is the full run (mode local, or ci when `CI=true`), `--measure-only` runs only the architecture and fitness checks (what gate step 5 calls). Setting `PIPELINE_CHECK_DIR` uses a working copy instead of the pinned tag. `tools/hooks/pre-push` runs `tools/pipeline-check.sh --pre-push`; it was the local stand-in for branch protection while the repository was private on GitHub's free plan, and since the repository became public (2026-11-06) it runs in addition to that protection: before a push the program runs the gate and the local checks, and a `falha` stops the push. It is enabled once per clone with `git config core.hooksPath tools/hooks` (set in this clone on 2026-11-02) and skipped on purpose with `git push --no-verify`. Which changed paths trigger the check is the `[pre_push] guard` list in `pipeline-check.toml`, which is empty (`guard = []`) in this repository; what the program does with `--pre-push` beyond the script's own comment was not verified. The collector transport test (`crates/collector/tests/transport.rs`) was hardened in 855ffd7: it now waits until the server answers a Ping, not only until its socket file exists, because the file appeared before the server accepted connections and the test failed on busy first runs.
