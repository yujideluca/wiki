## What it is
The Python code that studies the Radiopaedia articles and cases collected by [[radiopaedia-crawler]] and tries to map the words of a radiology report to likely diagnoses. It is the statistical part of [[radiology-report-matcher]]: it counts words and does arithmetic on them, and it is not an artificial-intelligence model. The plan is to build four competing versions of the mapping and score them all the same way; this package holds the shared tools, versions 1 and 4, and version 2 ([[radiology-v2]], scored on the outer halves by `v2_outer.py`). The folder is `analysis/` in `~/dev/radiology-crawler`, with one helper outside it, `tools/analysis_status.py`. Version 3 (step C4, the academic approach, [[radiology-v3]]) started from `docs/problem-formulation.md` (2026-11-08), a written statement of the problem as mathematics: rank about 7,200 diagnoses for a report's word counts so that the right one is in the first k as often as possible. It records facts that shape the model, such as that the test half only contains diagnoses that also have a tuning case, so diagnoses without any case are only wrong candidates there, and that version 2 is the score to beat. Version 3 was scored on 2026-11-08 and stays slightly below version 2 overall, while it ranks diagnoses with no teaching case much better (`docs/v3-report.md`).

## What it does
It provides the pieces below, each in its own file. Each piece has a requirement (rows AN-1 to AN-22 in `docs/REQUIREMENTS.md`) and a test tagged with it.

- A frozen copy of the articles, so every version reads the same data while the crawler keeps writing.
- A hardware layer that uses every processor thread and a graphics card (GPU, graphics processing unit) when there is one. The same code gives the same ranking on the processor alone.
- A scoring harness: for each diagnosis, half of its cases tune a model and half test it (a fixed random seed, so all versions see the same halves), and a ranking is scored by how often the true diagnosis is in the top 1, 5 and 10.
- Version 4, Giovanni's idea, in layers: a rule tagger that gives every article the same set of tags (patient group, sex, imaging method, body region, texture, brightness, margins, contrast uptake, side or number, symptoms); filters that, since 2026-11-05, remove a diagnosis only for a stated age or sex that the article contradicts, and only after the ranking (see Notes), or lower its score for the softer layers; a chooser of the next question to ask the user ("akinator" style, like the guessing game: ask what removes the most candidates); and a last layer that scores the wording of the report.
- Version 1, Claude's own model without prior bias: a smoothed word-probability model of each article, with the number of articles linking to a diagnosis as its starting weight.
- Tagging by [[codex]] and by Haiku (a small Claude model) with the same closed list of allowed values, and a comparison of the taggers.
- A scientific test of the list of filler words (words a radiologist uses when unsure, which carry little information), written down in `docs/filler-list-protocol.md` before any result.
- `tools/analysis_status.py`, the one place that records where the analysis stands.

## How it does it
- **Unknown is not no.** A tag layer the article never mentions is stored as unknown, which differs from a stated "no". Only a stated, contradicting fact removes a diagnosis; missing information never does. Instead the question chooser asks.
- **Wording layer.** Each diagnosis article becomes a weighted bag of words and word pairs using BM25 (a standard formula that gives more weight to rare, informative words); sections about imaging count fully and the rest of the article a little. In a report, words inside a negation get a negative sign, words after a hedge ("possibly") are softened, and filler words are dropped. The score is one sparse-matrix product (a table of numbers multiplied in bulk), run on the processor or the GPU, and the result lists the words that moved each score.
- **Tagging by models.** `analysis/codex_tags.py` sends one article per call in a new, throw-away [[codex]] session far below 250,000 tokens (Giovanni's limit), with the article marked as untrusted text. An answer outside the allowed values is rejected, not silently fixed. Results are appended one line per article, so a stop loses nothing and a restart tags only what is missing. `analysis/haiku_batches.py` cuts batches of 100 articles from the other end of the same queue for Haiku subagents and merges only valid answers.
- **Status record.** The state of the work is the file `docs/analysis-status.json`; `tools/analysis_status.py set STEP STATUS --note "..."` changes it, rewrites the readable copy `docs/ANALYSIS-STATUS.md` and rebuilds the plan site, so the three never disagree. Anyone continuing the work reads it first. `AGENTS.md` in the repository gives [[codex]] the same working notes that `CLAUDE.md` gives [[claude-code]].
- **One model set per language (since 2026-11-01).** Snapshots, the rule tagger, the wording layer, the version 1 model and the version 4 engine take a language (`en`, `de`, `pt`). Each language has its own frozen snapshot (German and Portuguese come from the translations, with the sections rebuilt from the translated headings) and its own data files in `analysis/wordlists/`: `tags.<lang>.json` (tag words), `lang.<lang>.json` (section headings and title words) and `wording.<lang>.json` (negation, hedging, filler and stop words). The German and Portuguese lists are starting lists, not yet tested on the real corpus, and scores per language wait for the translated cases.
- **Per-language tagging check (2026-11-01).** `analysis/codex_tags.py N LANG` repeats the tagging pilot on the German or Portuguese translations of the same 300 articles. Codex ran out of budget, so Haiku (a cheaper model) tagged them instead. Against the rule tagger the type agreement is 0.72 in both languages (English: 0.75), and modality and region are about as good as in English. The sex, single-or-multiple and texture word lists are weak and are the next to fix. Haiku reading the translation agrees with Codex reading the English at 0.89 on type, so the translations keep the content.
- **Text files are read and written as UTF-8 (since 2026-11-06).** UTF-8 is the usual way to store text so that letters such as ä, ß or ã survive. Python otherwise uses the computer's default text encoding, and after CuPy (the GPU array library) starts that default can be ASCII (plain English letters only), so a German or Portuguese character crashed a run halfway. Every text read and write in `analysis/` and `tools/` now names `encoding="utf-8"`. The test `tests/test_text_encoding.py` reads the code of every Python file in the project folder, `analysis/`, `tools/` and `site_src/` and fails when a text-mode read or write (`read_text`, `write_text`, `open`, `gzip.open`, `Path.open`) leaves the encoding out. Since 2026-11-08 no file is exempt: its `PENDING` set (files allowed to fail while they waited for the fix) is empty, and the last gap, the status read in `site_src/build.py`, names UTF-8 too.
- **`--help` is safe in every script (since 2026-11-06).** Each runnable script in `analysis/` and `tools/` reads its arguments with `argparse` (Python's standard argument reader) before doing any work, so `python3 script.py --help` only prints the usage and exits with code 0, and an unknown option is refused with exit code 2. Before, several scripts read their arguments by hand, and `--help` ran the real job: `filler_test.py` and `corpus.py` overwrote the tracked report `docs/filler-list-report.md`. The arguments that do work stayed the same (for example `corpus.py [LANG]`, language `en` by default; `codex_tags.py all` or `N [LANG]`). The test `tests/test_cli_help.py` runs every such script with `--help` and with an unknown option and fails if a tracked file changes. `filler_stage_b.py` now imports the `analysis` package before NumPy, because on the laptop NumPy is found only through the library folder that importing `analysis` adds.
- **Data stays local.** The snapshot, tags and results live in `data/analysis/`, which git ignores, like the rest of `data/`.

## Functions
- `corpus.make_snapshot`, `corpus.load_snapshot`: write the frozen article file with a count and checksum; read it back and refuse a file whose checksum changed.
- `hardware.detect`, `hardware.array_module`, `hardware.parallel_map`: find threads and GPU; return CuPy (GPU arrays) or NumPy (processor arrays); run a function over items on all threads.
- `harness.split_by_diagnosis`, `harness.topk_hit_rates`, `harness.diagnosis_label`, `harness.case_label`: split cases by diagnosis; score a ranking at top 1, 5 and 10; find the article a case belongs to by exact title or synonym (a name shared by two articles gives no label instead of a guess).
- `tagger.tag_article`, `tagger.tag_all`, `tagger.article_type`, `tagger.coverage`: tag articles from word lists kept as data in `analysis/wordlists/`; give the article's type; report how often each layer is unknown.
- `filters.build`, `filters.apply`, `filters.best_question`: build the filter model; apply the age and sex layers (and the soft layers) to a report's stated facts; choose the next question, only about age or sex and never about what the report already says.
- `wording.build_index`, `wording.read_report`, `wording.score`: index the diagnosis articles; read a report with negation, hedging and filler; rank the diagnoses.
- `pipeline.Engine`: version 4 end to end, from report text to a ranking and the next question.
- `v1_model.build`, `v1_model.rank`: version 1.
- `codex_tags.run_all`, `codex_tags.parse_answer`, `codex_tags.compare`: tag every missing article with Codex; validate an answer; compare two taggers.
- `haiku_batches.make`, `haiku_batches.merge`: cut batches for Haiku; merge valid answers.
- `tag_agreement.agreement`: how often the taggers agree with each other.
- `filler_test.run`, `filler_test.classify`, `filler_test.holm`: run the filler-word test; label a word filler, informative or undecided; correct for many tests at once (Holm's method).
- `filler_stage_b.run`, `filler_stage_b.classify`, `filler_stage_b.lift_row`: Stage B of the filler-list test (requirement AN-23): lift of each listed word in the true article against a random one, on tuning-half case texts, with a negative and an invented-word positive control; writes `docs/filler-list-report-stageB-<lang>.md`.
- `case_labels.label_cases`, `case_labels.assign_split`, `case_labels.build`: give each downloaded case the diagnosis article it belongs to ("exact" when its title or synonym equals an article; "linked" when the first article it links to is typed as a diagnosis; otherwise unlabelled, never guessed), split the labelled cases into tune and test halves with the fixed seed, and write a frozen label file without case text.
- `list_precision.phrase_precision`, `list_precision.weak_phrases`, `list_precision.prune`, `list_precision.agreement`: test each phrase of the German and Portuguese tag word lists against the Codex tags on a tuning half of the articles (half chosen by a hash of the article name), list phrases that fire often but agree rarely, and score a list on the untouched holdout half.
- `case_sets.build`, `case_sets.query_text_translated`, `case_sets.load`: join each labelled case with the text a user would type (presentation, patient data, findings; the discussion that names the answer is cut) for English, German and Portuguese.
- `evaluate.tune`, `evaluate.evaluate`, `evaluate.score_matrix`: tune version 1 on the tuning half only and score it on the test half, many reports at once.
- `demographics.read`, `demographics.age_class`: read the age class (neonate, infant, child, adult, elderly) and the sex that a report states about the patient, in English, German or Portuguese; durations such as "pain for 3 days" are never ages, and two different statements count as none.
- `v4_batch.parse`, `v4_batch.score`, `v4_batch.evaluate`, `v4_batch.tune`, `v4_batch.tune_index`: read many reports once, score any setting of the free numbers with matrix products only (the ranking equals `pipeline.Engine`), score the top 1, 5 and 10, and tune the numbers on the tuning half.
- `translation_check.flags_for`, `translation_check.parse_verdicts`, `translation_check.wilson`: the translation check (requirements TC-1 to TC-4; method in `docs/TRANSLATION-CHECK.md`). `flags_for` marks a German or Portuguese translation whose shape differs from its English source (missing title, much shorter or longer text, a different number of `## ` headings, numbers lost, English words left in, the other target language, a model remark, an untranslated title) with no model call; flagged items and a fixed-seed random sample go to a review queue that Claude reviews a few at a time (`parse_verdicts` accepts only `ok`, `minor` or `major` for an item of the batch); `wilson` gives the error rate's 95% interval per language, kind and translator. Its tests are in `tests/test_translation_check.py`, the pilot's in `tests/test_literature_cases.py`. `tools/translation_check_run.sh` runs it daily (one small worker) or before the weekly budget renews.
- `literature_cases.make_plan`, `literature_cases.extract`, `literature_cases.review_precision`: the C5 pilot (requirements AN-32 to AN-35) for diagnoses with fewer than 10 cases. It searches open-access PubMed Central case reports, keeps only explicit CC BY, CC BY-SA or CC0 licences and imaging-only sentences, and writes 100 random records for manual review to `data/analysis/c5-sample-check.md`, outside git because it quotes article text. `review_precision` counts the marked checkboxes; until they are marked, precision is not measured (`docs/c5-report.md`).
- `articles_only.Models`, `articles_only.tune`, `articles_only.score_language`, `articles_only.main`: versions 1, 2 and 3 rebuilt from the articles only (V1a, V2a, V3a; requirements AN-41 and AN-42). `tune` chooses each version's few free numbers from a grid fixed in the code, on the tuning half; `outer` scores the test or new half once and refuses a second run.
- `jobs.Job`, `jobs.read_all`, `jobs.summary`: live progress of long analysis jobs (requirement AN-45). A job writes one small file in `data/analysis/jobs/` (items done and failed, total, state, a note) at most every 2 seconds; `read_all` gives the plan site the unfinished jobs and those finished in the last two days, with rate per hour and time left, and shows a running job with no update for 10 minutes as not updating. Only counts and labels are written. The finding-tag run, the Codex article tagging (`codex_tags`) and the translation review (`translation_check review`) report through it; CLAUDE.md principle 14 makes it the rule for every job longer than a few minutes.
- `morph_tags.generate`, `morph_tags.check`, `morph_tags.run`, `morph_tags.build`, `morph_tags.characterize`, `morph_tags.main`: finding tags (step T2; requirements AN-43 and AN-44). For each diagnosis article, a fresh model session without web access lists the imaging findings the article describes, each with one to five wordings of exactly the same morphology in that language's standard radiology vocabulary and a quote from the article. A second fresh session with web search checks each finding against the article and the literature, and each wording for exact meaning. A finding is kept only if the article supports it, the literature does not contradict it and at least one wording is exact; only exact wordings are kept. `build` writes the tags as a separate dataset (`data/analysis/morph-tags-{lang}-{date}.jsonl.gz` with a manifest), so a model can be run with and without them. The `pilot` command plants wrong findings and wordings to test the checker; `characterize` counts what was kept, dropped and caught. `--engine` chooses the model: `sonnet` (headless Claude Code with no settings, hooks or saved session; web search is its only tool, and only in the check) or `codex` (OpenAI's coding agent, gpt-6.1-sol); each engine keeps its own raw files. A usage-limit refusal stops the run with exit code 75 (`UsageLimit`); rows already written are kept and a rerun resumes. `tools/morph_tags_full.sh` runs every language in turn. After each usage-limit stop it waits until the reset time named in the refusal message ("resets 9pm", read by `t2_check.py reset-epoch`; 30 minutes when the message names no time), then builds and characterizes each dataset.
- `t2_check.reset_epoch`, `t2_check.assess`, `t2_check.tick`, `t2_check.show`: the watchdog of the full finding-tag run (requirement AN-60). It uses no model tokens. Each check reads the unit's state, its log (the journal), the raw tag files and the progress files, and writes one line to `data/analysis/morph/t2-check.log` when something changes: LIMIT (a usage limit was hit, with the planned resume time), RESUMED (work started again and every check passed), REPAIRED (a wait went on more than 5 minutes past the reset, so the checker restarted the unit; the run picks up where it stopped), LANG_DONE, ALL_DONE, or PROBLEM (unreadable lines, articles tagged twice, too many failed rows, articles missing after a language finished, no progress for 20 minutes, or the unit stopped early). It runs every 3 minutes in a loop started from a Claude Code session. That loop ends on any event other than LIMIT and wakes the session to look at it. A permanent systemd timer was planned but not installed. Tests: `tests/test_t2_check.py`.
- `morph_audit.sample`, `morph_audit.audit_one`, `morph_audit.kappa`, `morph_audit.report`, `morph_audit.run`, `morph_audit.codex_cmd`: a second-engine check of the finding tags (requirements AN-46 and AN-47). Codex re-runs the fact-check on a random sample of articles Sonnet already tagged, on the same findings, with the same prompt and keep rule, and the two verdicts are compared finding by finding. Because Sonnet keeps almost every finding, Cohen's kappa (agreement corrected for chance) is misleading here, so the report leads with raw agreement, a 95 % interval, and how often Codex rejects what Sonnet kept; PABAK and Gwet's AC1 are agreement measures that stay stable when one rater says yes almost always. `codex_cmd` switches off the user's interactive Codex hooks (`-c features.codex_hooks=false`): scripts that run automatically inside every Codex session, which in a batch call only cost tokens.
- `v2_tagged.Model`, `v2_tagged.run`, `v2_tagged.choose`, `v2_tagged.AuditGuard`, `v2_tagged.main`: version 2 with finding tags ("V2t", step S1c; requirements AN-48 to AN-50; design `docs/s1c-v2t-design.md`, decision record ADR-0004, an architecture decision record). `Model` scores each diagnosis article with BM25 (a standard word-weighting formula for ranking documents) on the whole article and on its imaging sections, plus a separate channel that compares the report with the article's finding tags: the best-matching wording of each finding, then the top three findings weighted 4:2:1. A diagnosis without tags keeps its article score and gets zero from the tag channel. `run` tunes two weights (the imaging-section weight `f` and the tag weight `lambda`) on a 12-setting grid fixed in advance, on the tuning half only, using version 2's split of that half; `choose` picks by top-10, then top-5, then top-1 hits. The chosen setting is saved before a single audit run on the held-back part of the tuning half, and `AuditGuard` refuses a second audit. Scoring is sparse-matrix arithmetic in 64-bit floats on the CPU; ties count against the right diagnosis. Its tests are in `tests/test_v2_tagged.py`; the results are in `docs/s1c-v2t-report-provisional.md`.
- `v4_tagged.Model`, `v4_tagged.Parser`, `v4_tagged.Params`, `v4_tagged_run.run`, `v4_tagged_run.main`, `v4_tagged_check.check`: version 4 with finding tags ("V4t", step S1c; requirements AN-51 to AN-53; design `docs/s1c-v4t-design.md`, decision record ADR-0005). Version 4 follows Giovanni's modelling directives (layered filters, demographic questions, a wording layer). `Model` keeps two separate channels: the article text and the finding wordings, each scored with BM25 over all articles and each scaled so its weights sum to 1 per diagnosis (unit L1 normalization, fixed by the design); `Parser` handles negation, hedging words, filler words and demographic exclusions in the report. `run` tunes on the fit and selection parts with grids fixed in advance (12 settings with tags, 4 without), saves the choice, then runs the one-time audit. `v4_tagged_check` is a diagnostic on the fit and selection parts only: in English, plain BM25 finds the right diagnosis in the top 10 for 59.8 % of fit reports, and the unit L1 step lowers this to 23.4 %, which explains the low V4t scores. A first version had an arithmetic precision defect; the corrected rerun (`-fix1`) gave exactly the same results. Two patch files keep the history of the code: `docs/s1c-v4t-cache.patch` (a speed-up that precomputes demographic and contradiction counts, with no change to results) and `docs/s1c-v4t-fix1.patch` (the arithmetic correction); applying both in reverse gives back the code that produced the original runs. Tests: `tests/test_v4_tagged.py`; results: `docs/s1c-v4t-report-provisional.md`.
- `v3_tagged.Model`, `v3_tagged.frozen_model`, `v3_tagged.Processor`, `v3t_run.tune`, `v3t_run.audit_claim`, `v3t_run.load_frozen`, `v3t_run.main`: version 3 with finding tags ("V3t", step S1c; requirements AN-54 to AN-56; design `docs/s1c-v3t-design.md`, decision record ADR-0006). Version 3 is the academic version, designed jointly by Claude and Codex. `Model` ranks diagnosis articles with Jelinek-Mercer smoothing (a language-model scoring method that mixes each article's word frequencies with the whole collection's, weight `rho`), built from the articles only, after `Processor` drops excluded article sections (such as differential diagnosis and references) and negated phrases using the fixed word lists in `analysis/wordlists/v3t.json`. A finding tag adds a non-negative bonus (weight `beta`) only when one of its wordings appears in the report exactly; `beta` 0 gives exactly the tag-free model. Scores are 64-bit integers (fixed point), so ranks are exact and repeatable. `tune` tries a 16-setting grid fixed in advance on the fit and selection parts of the tuning half (version 2's split) and chooses the no-tags setting separately; `audit_claim` writes a one-use record before the held-back audit part is read, so a second audit, or one after an interruption, is refused. Each run records the hashes of its code and word lists and stops if they change while it runs. Tests: `tests/test_v3_tagged.py`; results: `docs/s1c-v3t-report-provisional.md`.
- `sanity.main`: a machinery check on the cases downloaded so far; it is not the real evaluation.

## Where it sits in the pipeline
After [[radiopaedia-crawler]], which supplies the articles and cases in the database. It reads the German and Portuguese article translations produced by [[report-translator]] when building those language snapshots. It is the base for the planned numerical engine of [[radiology-report-matcher]].

## Who receives its output
Giovanni, through the step-by-step guide on the home page of the plan site and through `docs/ANALYSIS-STATUS.md`; later the planned matching engine.

On 2026-11-05 the dangerous-miss analysis (step S3) found why version 4 missed diagnoses: the article age tags held the typical age group (acute pancreatitis: child) and the filter read them as "only these", so a stated adult age removed the true diagnosis in 1,497 of 20,849 English tuning cases. Against the real ages in the tuning cases the rule tags were contradicted in 25.3% of cases and the LLM tags in 10.7% (`tag_merge.audit`, requirement AN-24).
